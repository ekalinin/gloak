# P4's second cut, B and C together: the remaining eleven operations

Date: 2026-08-29
Spec: `docs/superpowers/specs/2026-08-29-p4-multi-realm-design.md`
Follows: `docs/superpowers/plans/2026-08-29-p4-realm-crud.md`

Cut A served five of P4's sixteen operations. This plan serves the other
eleven, and it merges the design's cuts B and C into one because the
measurement that was supposed to make B expensive did not.

## Task 1: the measurement that decides the shape of the cut

**Done 2026-08-29**, against `quay.io/keycloak/keycloak:26.7.1 start-dev` on
port 8086, every transcript printed from the argv that was executed.

The design says a created realm carries four keys where Gloak mints three and
"the fourth is an AES key Gloak has no model for", and calls that a key manager
change rather than a handler. Measured, the fourth key is the cheapest part of
the endpoint and three other things about it are not.

### 1.1 The body

```
GET /admin/realms/{realm}/keys
200, Content-Type: application/json;charset=UTF-8, Cache-Control: no-cache,
the five security headers.

{"active":{"RSA-OAEP":"<kid>","HS512":"<kid>","RS256":"<kid>","AES":"<kid>"},
 "keys":[ ...four... ]}
```

One key entry, in declared order, with three fields absent on an `OCT` key:

```
providerId, providerPriority, kid, status, type, algorithm,
publicKey, certificate, use, validTo
```

| type | algorithm | use | publicKey/certificate/validTo | kid |
|---|---|---|---|---|
| RSA | RS256 | SIG | present | 43-char base64url |
| RSA | RSA-OAEP | ENC | present | 43-char base64url |
| OCT | HS512 | SIG | absent | UUID |
| OCT | AES | ENC | absent | UUID |

`providerPriority` is 100 on all four; `status` is `ACTIVE` on all four; `use`
is upper case here where the JWKS spells it `sig`/`enc`. `validTo` is the
certificate's `notAfter` in milliseconds.

### 1.2 The four things the design did not predict

**`active` is a Java map and `internal/javamap` already reproduces it.** The
measured order is `RSA-OAEP, HS512, RS256, AES` on master and on a created
realm alike, and `javamap.KeyOrder` returns exactly that - a fifth confirmed
vector, and the first with no bucket collision in it. So `active` is not a Go
map marshalled alphabetically and not a struct either: the algorithm names are
data.

**The `keys` array is ordered by `providerId`, which is a random UUID.**
master came back `501bb07d, c64d81a4, c801ee0a, cdaa5860` and the created realm
`3a8bb3b7, 5ab0fbec, bf17f8cb, df836b05` - both ascending, and the algorithm
order differs between them. So the array has no reproducible order and the case
needs `Case.Unordered`, like the JWKS beside it.

**Keycloak's RSA `kid` is `base64url(sha256(SPKI DER))`.** Computed from the
measured `publicKey` of master's RS256 key it reproduces the measured `kid`
byte for byte. It is not the RFC 7638 JWK thumbprint, which was tried first and
gives a different value. Gloak mints a UUID there today. The two OCT keys' kids
really are UUIDs, so the rule is per key type.

**`providerId` is not the `kid`.** It is the id of the key provider
*component*, an object Gloak does not model.

### 1.3 What that makes the key work

Two changes in `internal/keys`, not a rewrite:

- a fourth key, `OCT`/`AES`, `use` ENC, secret bytes, never published in JWKS;
- `kid` for the two RSA keys becomes the measured digest.

`providerId` is **derived** from the key row id rather than stored. Each of
Keycloak's four keys comes from exactly one component, so in Gloak the key row
and the component are the same object; deriving keeps the value stable across
restarts, keeps it distinct from the `kid` as measured, and avoids a column for
a concept nothing else in the model has. It is masked by `Case.Volatile` in the
golden either way, which is a reason to keep it simple and not a reason to make
it wrong.

## Task 2: the fourth key, and the measured kid

`internal/keys/keys.go`, `internal/keys/manager.go`.

`RealmKeys` gains `AESKeyID string` and `aesKey []byte`. `Generate` mints 16
random bytes for it - Keycloak's `aes-generated` provider default, and not
observable through any endpoint, since the secret is never published. `rows`
gains a fourth row, `algorithm = "AES"`, `key_use = "enc"`. No migration:
`realm_key` already keys on `(realm_id, algorithm)`.

`kidFor(pub *rsa.PublicKey)` is `base64url(sha256(x509.MarshalPKIXPublicKey))`,
and `Generate` uses it for `RSAKeyID` and `EncKeyID`. `HMACKeyID` and
`AESKeyID` stay `model.NewID()`, measured.

**A realm whose keys predate this cut has three rows and must not be declared
corrupt.** `load` reports an incomplete set today, which would turn every
existing store into a startup failure. The AES key is published in no JWKS and
signs nothing, so minting the missing one and persisting it cannot invalidate
anything a client cached - unlike the RSA or HMAC keys, whose absence `load`
must go on refusing. That asymmetry is the whole reason this is a special case
and it is written down at the call site.

Tests: the measured vector - master's recorded `publicKey` in, its recorded
`kid` out - and a round trip proving the AES key survives a restart with the
same id, plus a realm with three rows gaining a fourth and keeping the other
three ids.

Commit: `feat(keys): a realm's fourth key, and the measured RSA kid`

## Task 3: `GET /admin/realms/{realm}/keys`

`internal/admin/keys.go` (new), `internal/admin/router.go`.

The representation is a struct per key with the ten fields in the measured
order, `omitempty` on `publicKey`, `certificate` and `validTo` - all three
absent on an OCT key, and all three of a type `omitempty` drops when empty,
which is why `validTo` is a `*int64`.

`active` is `map[string]string` written out through `javamap.KeyOrder`, the
same way `internal/admin` already writes `clientMappings`.

Guard: `view-realm` or `manage-realm`, measured across all 22
`realm-management` roles plus a caller holding none. `realm-admin` reaches it
through its composites. An unknown realm is 404 `Realm not found.` before any
role check, and no token at all is 401 before the realm is resolved.

Commit: `feat(admin): a realm's key set, four keys`

## Task 4: the store learns a realm's default groups

`internal/store/store.go`, both drivers, **`0013_default_group.sql`** in each -
0012 is Cut A's `realm_settings`, already on main, so this cut's number is 13
and not the 12 the task predicted.

```sql
CREATE TABLE realm_default_group (
    realm_id TEXT NOT NULL REFERENCES realm(id) ON DELETE CASCADE,
    group_id TEXT NOT NULL REFERENCES keycloak_group (id) ON DELETE CASCADE,
    PRIMARY KEY (realm_id, group_id)
);
```

The cascade off `keycloak_group` is measured, not tidiness: deleting a group
that was a default group removed it from the listing.

`GroupRepo` gains three methods, on the group repo rather than the realm repo
because every one of them returns or takes a group and the join table's other
end is what cascades:

```go
ListDefaultGroups(ctx, realmID) ([]*model.Group, error)
AddDefaultGroup(ctx, realmID, groupID) error     // idempotent, measured 204 twice
RemoveDefaultGroup(ctx, realmID, groupID) error  // no error when absent, measured 204
```

`internal/store/storetest` gains a subtest for all three plus the cascade,
because "the DDL says so" is not evidence that both drivers act on it.

Verify: `CGO_ENABLED=0 go test ./internal/store/...`, then
`go test -tags docker ./internal/store/postgres/` by hand, both outputs in the
commit body.

Commit: `feat(store): a realm's default groups`

## Task 5: default groups and group by path

`internal/admin/defaultgroups.go` (new), `internal/admin/router.go`.

**Four operations, three guards, and no two of them are the same shape.**

| Route | Roles | Order |
|---|---|---|
| `GET .../default-groups` | `view-realm`, `manage-realm` | realm, caller, role |
| `PUT .../default-groups/{groupId}` | `manage-realm` | realm, caller, **role, then group** |
| `DELETE .../default-groups/{groupId}` | `manage-realm` | same |
| `GET .../group-by-path/{path}` | `view-users`, `manage-users` | realm, caller, **group, then role** |

The two middle rows are the finding. AGENTS.md records that "a group is
resolved before the caller is judged at all. Every route naming a `{groupID}`
answers 404 for a group that does not exist to **every** caller". These two do
not: an unknown group id answers **403** to a caller holding `view-realm`, and
403 to a caller holding no admin role at all. Measured on both verbs. So the
rule holds on the `Groups`-tagged routes and is inverted on the two
`Realms Admin`-tagged ones that name a group, which is the third time this
project has met a rule that is right on one family and wrong on its neighbour.
`guardAny(realmWriteRoles, ...)` is therefore the right combinator and
`guardGroup` is the wrong one, and the handler resolves the group itself.

`group-by-path` does take `guardGroup`'s order - an unknown path is 404 to
every caller - so it gets a `guardGroupPath` combinator that resolves the path
and hands the group over. It is **not** opened by `query-groups`, which opens
the group listing and the count; `view-users` and `manage-users` and nothing
else.

Two bodies, and they are the sixth and seventh shapes of one group:

- `group-by-path` is `groupFull` **minus `access`**. Measured side by side
  against `GET /groups/{id}` on the same group: identical but for that one key.
  `briefRepresentation` does nothing to it.
- a `default-groups` entry is exactly `groupMembership` - `id, name, path,
  [parentId], subGroups` - the shape a user's group listing already uses.
  `briefRepresentation` does nothing to it either.

So `groupShape` gains one constant and reuses one.

Errors:

```
GET  .../group-by-path/{miss}      -> 404 {"error":"Group path does not exist"}
PUT|DELETE .../default-groups/{miss} -> 404 {"error":"Group not found"}
```

`Group path does not exist` is a **twelfth** spelling of not-found on the admin
API. `Group not found` is the eleventh, already written down for the membership
route, and this is a second place it is used - which is why it goes through the
existing `writeGroupNotFound`'s sibling rather than being typed again.

The `default-groups` listing has **no reproducible order**: three groups added
`zzz, aaa, mmm` came back in that order, and in another realm a parent added
first and a child added second came back child first. Neither name, id, path
nor insertion order explains both, so the case takes `Case.Unordered: ["."]`.

A `PUT`'s 204 carries `Cache-Control: no-cache`, which AGENTS.md's rule says no
`PUT` does. See the handover: the request carried no `Content-Type`, so it also
correctly omits `X-Frame-Options`, and `httpx.WriteNoContent` needs the
`Cache-Control` decision per endpoint as it already documents.

Commit: `feat(admin): a realm's default groups, and a group by path`

## Task 6: client policies and client profiles

`internal/admin/clientpolicies.go` (new), `internal/admin/realmrep.go`.

The state already exists. `clientProfiles` and `clientPolicies` are two of the
104 keys of the realm representation, which Cut A stores in the settings blob,
and they are the same state these four operations read and write: a
`PUT .../client-policies/profiles` was measured changing what
`GET /admin/realms/{realm}` answers, and a `PUT /admin/realms/{realm}` carrying
`clientProfiles` was measured changing what
`GET .../client-policies/profiles` answers. So there is no migration and no new
column - only `clientProfile` and `clientPolicy`, which Cut A left as empty
placeholder structs, gaining the measured fields.

```go
type clientProfile struct {
    Name        string             `json:"name"`
    Description string             `json:"description,omitempty"`
    Executors   []clientExecutor   `json:"executors"`
}
type clientExecutor struct {
    Executor      string         `json:"executor"`
    Configuration map[string]any `json:"configuration"`
}
type clientPolicy struct {
    Name        string            `json:"name"`
    Description string            `json:"description,omitempty"`
    Enabled     bool              `json:"enabled,omitempty"`
    Conditions  []clientCondition `json:"conditions"`
    Profiles    []string          `json:"profiles"`
}
```

Measured: a profile written without a description comes back without the key,
and a policy written without `enabled` comes back without it, so `omitempty` on
those two is the contract rather than a convenience. `configuration` is a free
JSON object and stays `map[string]any`; nothing in P4 interprets it.

The reads take a query parameter each:

```
?include-global-policies=true  adds "globalPolicies":[]
?include-global-profiles=true  adds "globalProfiles":[ ...ten... ]
```

The ten global profiles are a 6 KB constant of Keycloak's built-in FAPI,
OAuth 2.1 and SAML profiles. They are recorded verbatim into
`internal/admin/testdata/global-client-profiles.json` and served through
`json.RawMessage`, because marshalling them from Go structs would put every
`configuration` map's keys in Go's alphabetical order and the recorded ones are
not alphabetical. That is a second, narrower use of the same reasoning
`browserSecurityHeaders` already carries, and it is why the constant is data
and not code.

Guards: `view-realm` or `manage-realm` to read, `manage-realm` to write,
measured on all four routes.

Errors, and this endpoint has **three** families like the realm resource:

```
PUT profiles, malformed        -> 400 {"error":"invalid_request","error_description":"Cannot parse the JSON"}
PUT profiles, no body          -> 400 {"errorMessage":"Passing null clientProfiles not allowed"}
PUT profiles, unknown field    -> 400 {"error":"Invalid json representation for ClientProfilesRepresentation. Unrecognized field \"nosuchfield\" at line 1 column 20."}
PUT profiles, unknown executor -> 400 {"errorMessage":"proposed client profile contains the executor, which does not have valid provider, or has invalid configuration."}
PUT policies, unknown profile  -> 400 {"errorMessage":"Policy pol-b contains invalid profile nope"}
```

**A `PUT` with no body is a 400 here where `PUT /admin/realms/{realm}` is a
500.** Same verb, same resource family, two answers; the shared decoder that
Cut A's plan warned about would get this one wrong too.

The 204 from either `PUT` carries **no `Cache-Control` at all**, where
`PUT .../default-groups/{id}` carries `no-cache`. Two `PUT`s in one cut,
opposite answers, which is what "pinned per endpoint" means.

Validation: the executor list and the condition list are Keycloak's registered
provider names. This cut validates **only what it can name**: a policy naming a
profile that is not in the realm's own profiles is the measured 400 above, and
it needs no provider inventory. The executor and condition inventories are the
authentication and client-policy engines' - P8's and P5's - so an unknown
executor is a divergence this cut records rather than fixes, and the case for
it is `Recorded`, not `Implemented`.

Commit: `feat(admin): a realm's client policies and client profiles`

## Task 7: client types, and the contract is a 501

`internal/admin/router.go`.

`GET` and `PUT /admin/realms/{realm}/client-types` answer

```
501 {"error":"Feature not enabled","error_description":"For more on this error consult the server log."}
```

on a default 26.7.1, `Content-Type: application/json`, no `Cache-Control`.
`CLIENT_TYPES` is a disabled preview feature. This is the same situation as
`GET .../client-secret/rotated`, whose permanent 404 AGENTS.md already records
as the contract rather than a stub, and that case carries an `Operation`, so
these two do.

**The order is measured and it is not the neighbouring routes'.** No token is
401; a bad token is 401; an unknown realm with a valid token is 404
`Realm not found.`; and then **every** authenticated caller gets the 501,
including one holding no admin role at all. So the feature check runs after the
realm and *before* the authorization check, which no other route in this cut
does - hence a combinator that authenticates, resolves the realm, and answers,
with no role list to get wrong.

Commit: `feat(admin): client types, a disabled preview feature`

## Task 8: the cases and the goldens

`internal/conformance/catalog_admin.go`, appended at the very end of the
Catalog slice, and `internal/conformance/fixture.go`.

Fixtures: Cut A's realm-creating fixtures are the model. This cut needs one
realm with a group tree and a default group in it, built through `Steps`.

`PristineRealm` accounting, because this cut adds state to master:

- **nothing here creates a group in master.** The group fixtures live in the
  created realm, so master's `GET /groups` golden is untouched.
- `GET /admin/realms/master/keys` is a realm-wide read and takes
  `PristineRealm: true`. It is not perturbed by other fixtures - nothing
  creates a key - but the flag costs nothing and states the intent.

Cases, `admin/realms-admin/...` and `admin/key/...` so `chapterOf` puts them in
the right denominator:

| Case | Status |
|---|---|

| default-groups put, delete, delete-again, unknown id, wrong role | Implemented |

## What this plan deliberately does not do

**It does not join a new user to the realm's default groups.** Measured: a user
created by `POST /users` in a realm with two default groups came back a member
of both. That is `POST /users`' behaviour, P2's, and it changes no existing
golden because master has no default groups - but it is a divergence the moment
this cut makes default groups settable. It is Task 10 if there is room and a
follow-up if there is not.

**It does not implement the client-policy engine.** Serving a field is not
implementing it, as the design's section 10 says of the realm's 104. Nothing in
Gloak enforces a client policy, and nothing in this cut claims to.

**It does not validate executor or condition provider names.** See Task 6.

**It does not move client policies to P5.** Section 2 of the design assigns
them to P4 and calls it a judgement; this cut acts on the judgement without
re-litigating it.
