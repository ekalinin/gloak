# CIBA and DPoP: what would lift each, and what this cut takes

Five cases in `internal/conformance`'s OIDC chapters are unserved for two
reasons that were re-checked on 2026-09-06 and held. This document decides what
happens to each. It leads with the two questions the brief asked to be answered
before any design, because both answers changed the shape of the work.

Everything below was measured against live Keycloak 26.7.1 containers started
for this cut on 2026-09-06 and removed at the end of it. Two containers were
used and they differ in **one startup option**; that difference is the whole of
the CIBA finding.

## 1. DPoP

### 1.1 What a default container does with a proof

DPoP is `"type":"DEFAULT","enabled":true` in `GET /admin/serverinfo`, so nothing
was switched on to measure any of this.

A proof signed ES256 over a P-256 key, with `typ: dpop+jwt`, a `jwk` header and
the four claims `htm`, `htu`, `iat`, `jti`, answers **200** on the password
grant at `admin-cli`, which carries no `dpop.bound.access.tokens` attribute at
all. The response's key set is unchanged, and `token_type` is `DPoP` where the
same request without the header answers `Bearer`. So **DPoP verification is
opportunistic**: the header, not the client, turns it on.

`cnf` is on the **access and refresh tokens and not on the ID token**, and it
sits immediately before `scope` on both:

```
access  exp iat jti iss typ azp sid cnf scope                    (admin-cli, lightweight)
access  exp iat jti iss aud sub typ azp sid acr realm_access
        resource_access cnf scope email_verified preferred_username
refresh exp iat jti iss aud sub typ azp sid cnf scope aud_x prov
id      exp iat jti iss aud sub typ azp sid at_hash acr …        (no cnf)
```

Its value is `{"jkt":"<RFC 7638 thumbprint>","kc-jkt-type":"DPoP"}` - two keys,
and the second is Keycloak's own.

**The refusal ladder, measured one malformation at a time**, all 400 with
`invalid_request` on the token endpoint:

```
not a JWT at all              DPoP header verification failure
typ: JWT                      Invalid or missing type in DPoP header: JWT
alg: none / HS256             Unsupported DPoP algorithm: none
no jwk in the header           No JWK in DPoP header
signature does not verify     DPoP verification failure: org.keycloak.exceptions.\
                              TokenSignatureInvalidException: Invalid token signature
alg RS256 over an EC key      Key with algorithm RS256 and type EC is incorrect \
                              for provider algorithm RS256
any of htm/htu/iat/jti absent  DPoP mandatory claims are missing
htu names another URL          DPoP HTTP URL mismatch
htm names another method       DPoP HTTP method mismatch
iat outside the window         DPoP proof is not active
the same jti twice             DPoP proof has already been used
the header present and empty   DPoP proof is missing
```

**The order is measured rather than chosen**, by nine proofs each wrong in two
ways: `typ` first, then `alg`, then the `jwk`, then the signature, then the
mandatory-claim set, then **`htu` before `htm`**, then `iat`, then `jti`. A
proof with a broken signature and a wrong `htm` answers about the signature; one
with a wrong `htm` and a missing `jti` answers about the claims; one with a
wrong `htm` and a wrong `htu` answers about the URL.

**The `iat` window is forty seconds wide**, `[now-25, now+15]`, measured at one
second's resolution against a container whose clock agrees with the host's to
the second. `iat = now-25` is a **500**, not a 200 and not the 400 either side
of it: it passes the window and dies where the `jti` is stored, which is what a
lifetime of 10 and a skew of 15 predict when the cache entry's remaining life
computes to zero. `now-26` is the ordinary "not active".

Two more that decide where the check goes. **The proof is verified after client
authentication and after the duplicated-parameter check and before the grant's
own work** - a bad proof with a wrong password answers about the proof, a bad
proof with an unknown `client_id` answers `invalid_client`, and a bad proof with
`zz` twice answers `duplicated parameter`. And **it is one check for every
grant**: `password`, `client_credentials`, `refresh_token`, the device grant and
the CIBA grant all answer the same sentence for the same bad header.

The refresh grant carries the binding: a bound refresh token refreshed with a
proof from the same key answers 200 with the same `cnf`, with a proof from
another key answers 400 `invalid_grant` `DPoP confirmation doesn't match DPoP
proof`, and with no proof at all answers 400 `invalid_grant` `DPoP proof is
missing`.

A client carrying `dpop.bound.access.tokens: "true"` answers a request with no
header at all `DPoP proof is missing` - the same sentence an empty header gets
from a client that does not require one.

### 1.2 What RFC 9449 requires of the server

Proof verification as above; `cnf.jkt` on the tokens; `token_type: DPoP`; the
binding re-checked on the refresh; and, at the resource server, the `DPoP`
authorization scheme with an `ath` claim binding the proof to the token.

The last of those was measured and is **deliberately out of this cut**.
`userinfo` on 26.7.1 refuses `admin-cli`'s access token whatever the scheme,
because it is a lightweight token - the control says so:

```
unbound + Bearer          401  Lightweight access token not allowed for userinfo endpoint
bound + DPoP + ath proof  401  Lightweight access token not allowed for userinfo endpoint
bound + proof without ath 401  Token verification failed
bound + no proof          401  Token verification failed
bound + Bearer scheme     401  Token verification failed
```

which does say something worth keeping - the DPoP check runs **before** the
lightweight-token refusal, `ath` is required, and a bound token presented as a
`Bearer` is refused - but a case that measures it needs a non-lightweight client
with `openid`, and no case in the catalogue wants one today. Filed rather than
built.

### 1.3 What a harness hook would have to compute, and how tight it is

**The reason on `oidc/token/dpop-bound-token` is right about the 200 and wrong
about everything else, and this is the finding that changes the shape of the
work.** Every structural check above runs *before* the `iat` window and the
`jti` cache. A proof minted stale on purpose therefore answers the **same
sentence forever**, which was checked by sending the identical bytes twice:

```
stale + typ=JWT (2)   Invalid or missing type in DPoP header: JWT
stale + typ=JWT (3)   Invalid or missing type in DPoP header: JWT
stale + no jwk (2)    No JWK in DPoP header
stale + no jwk (3)    No JWK in DPoP header
```

So **eight of the twelve refusals are expressible as a literal proof committed
to the catalogue**, including "DPoP proof is not active" itself, and they need
nothing from the harness at all. What genuinely cannot be a literal is the
**200** and the two refresh refusals, because all three need a proof the server
will accept.

For those three the harness has to compute one value, and the two halves of the
old reason are worth separating:

- The **`jti`** half is real and a computed value answers it: minted per run,
  used once, and it never reaches a golden.
- The **`iat`** half is much weaker than it reads. The window is forty seconds
  and a fixture's last step is one HTTP round trip before the case's request. A
  proof minted at the start of `Run` is nowhere near stale.
- The half the re-check added is the true one: **`Step` computes nothing**, and
  all four capture forms read a value out of a response. There is nowhere to
  sign anything.
- And one the re-check did not have: **`htu` must be the case's own absolute
  URL**, which differs between the recorder (the container's mapped port) and
  the verifier (`testIssuer`). So the value cannot be a constant either; it has
  to be computed **from `base`**, which `Run` has and `Expand` does not.

The mechanism that follows is one field on `Fixture` and one function: a map of
name to `{key, method, path}`, computed once at the top of `Run` from `base`,
put into the same `vars` every `{{name}}` already comes from. Steps stay exactly
what they are - a request and four captures - and the fixture is what computes.
The key is a **fixed constant**, so `cnf.jkt` is a stable byte string rather
than a mask.

### 1.4 Is it worth two operations

Yes, and the cost is smaller than the count of measurements suggests, for three
reasons. The check has **one insertion point** - `token()` already has the
measured order and the proof goes between `hasDuplicate` and the grant switch.
The claim change is **three struct fields** in a measured position. And eight of
the eleven new cases are literals that need no mechanism.

Against F38's rule - do not build a mechanism this cut does not use - the mint
has **three** consumers here, not one: the bound token, and the two refresh
refusals, whose fixtures need a bound token before the case's own request can be
wrong about it.

**Decision: take DPoP's token-endpoint half.** The resource-server half and the
authorization endpoint's `dpop_jkt` parameter are filed.

## 2. CIBA

### 2.1 Whether a decoupled channel is reachable from the recorder, measured

It is reachable from a **process**, and it was measured rather than reasoned. A
second container was started with one option added to `start-dev`:

```
--spi-ciba-auth-channel--ciba-http-auth-channel--http-authentication-channel-uri=\
  http://host.docker.internal:9099/ciba
--add-host=host.docker.internal:host-gateway
```

and a listener was stood up on the host. The container called out to it:

```
POST /ciba
  Authorization: Bearer <RS256 JWT, azp=gloak-probe-ciba, aud=the realm>
  Content-Type: application/json
  {"scope":"openid roles profile email","binding_message":"gloak-probe",
   "login_hint":"admin","is_consent_required":false}
```

The listener answered 201, replayed the bearer to
`POST /realms/master/protocol/openid-connect/ext/ciba/auth/callback` with
`{"status":"SUCCEED"}`, and the whole flow completed:

```
authentication request  200  {"auth_req_id":"<JWE>","expires_in":120,"interval":5}
poll, pending           400  authorization_pending | The authorization request is still
                             pending as the end-user hasn't yet been authenticated.
poll again, at once     400  slow_down | too early to access
poll after approval     200  nine keys, token_type Bearer, Cache-Control: no-store,
                             Pragma: no-cache
```

**The control is the whole finding.** The identical request, from an identically
created client, against the container that differs only in that option:

```
503  {"error":"server_error","error_description":"Failed to send authentication request"}
```

and both containers answer an unknown `auth_req_id` identically. So the 503 is
**not a property of Keycloak and not a missing feature**: `CIBA` is
`"type":"DEFAULT","enabled":true` on both. It is the artefact of a startup
option this project's recorder does not set. That is a different sentence from
the one three cases carry today, and it is the sharpening this cut owes them.

The option is not reachable from the running server either: `ciba-auth-channel`
is `"internal": true` in `GET /admin/serverinfo` with one provider and no
component type, and
`GET /admin/realms/master/components?type=…AuthenticationChannelProvider` is
`[]`. The realm carries four CIBA attributes - `cibaBackchannelTokenDeliveryMode`,
`cibaExpiresIn`, `cibaInterval`, `cibaAuthRequestedUserHint` - and the channel
URI is not among them.

### 2.2 What would lift the three cases, and why none of it is this cut's

Four things, and three of them are outside the files this cut owns:

1. **The recorder's container must carry the option**, and must be started with
   a host alias it can call back through. `startKeycloak` is in
   `record_test.go`, which this cut may not touch, and it starts `start-dev`
   with no options at all.
2. **The recorder must stand up a listener before the container starts** and
   pass its address in. Same file.
3. **`Fixture` has no lifecycle and `Run` has no inbound direction.** A fixture
   is `{State, Steps, Delay}`; `Run` sends a request and reads a response, four
   ways. `poll-complete` and `ciba-grant` need a value that arrives at the
   harness **as a request** - the callout - and there is no shape in the harness
   for one. This is F122's boundary exactly: an endpoint Keycloak calls *out*
   to, which the back-channel logout work declared structurally unreachable, and
   the measurement above says the boundary is the harness's rather than
   Docker's.
4. **The verifier must serve CIBA in process**, which means Gloak minting the
   JWE `auth_req_id`, making the outbound POST, serving the callback endpoint,
   and running the `authorization_pending`/`slow_down` state machine off the
   realm's `cibaInterval` and `cibaExpiresIn`. That is the work, and it is
   pointless until 1-3 exist, because nothing could record what it should
   answer.

`poll-pending` alone needs only 1, 2 and 4 - it wants an `auth_req_id` and not
an approval - so it is the cheapest of the three and still needs a file this cut
may not edit.

**Decision: refuse all three, and rewrite their reasons.** The reason as written
- "a default 26.7.1 has no CIBA authentication channel" - is true and reads like
a fact about Keycloak. It should say what the measurement says: a startup option
lifts the 503, the recorder does not set it, and the callout is a direction the
harness has not got.

## 3. The work

Committed before any edit a mutation pass will revert, and each claim below gets
a different mutation against a named test.

### Task 1 - `internal/oidc/dpop.go`, proof verification

The ladder of §1.1 in the measured order, as one function returning the
thumbprint or a named refusal. `go-jose/v4` is already a direct dependency and
reads a `jwk` header; no dependency is added. The single-use `jti` is an
in-memory store with an expiry, F75's shape: Keycloak keeps it in Infinispan and
Gloak keeps the authentication session, the authorization code and the device
store in memory for the same reason.

The `iat` window's constants are the measured ones - a lifetime of 10 and a skew
of 15 - and the 500 at exactly `now-25` is **not** reproduced: it is a Keycloak
defect that needs a cache whose put refuses a zero lifespan, nothing observes it
in this repository, and inventing a 500 to match one second of a window is the
kind of tidy-up this project files rather than builds.

### Task 2 - the binding on the tokens

`Cnf` before `Scope` on `accessClaims`, `lightweightClaims` and `refreshClaims`,
`omitempty`, and nothing on the ID token. `token_type` becomes `DPoP` when a
proof was accepted. The refresh grant re-checks the presented refresh token's
`cnf.jkt` against the proof's.

### Task 3 - the harness mint

One field on `Fixture`, one function, computed at the top of `Run` from `base`.
Three consumers.

### Task 4 - the cases

Eight literals, three minted, one promotion:

```
dpop-header-invalid        Recorded -> Implemented   (exists)
dpop-bound-token           Pending  -> Implemented   minted
dpop-proof-missing         new, literal, a client carrying the attribute
dpop-wrong-type            new, literal
dpop-unsupported-alg       new, literal
dpop-no-jwk                new, literal
dpop-signature-invalid     new, literal
dpop-missing-claims        new, literal
dpop-htu-mismatch          new, literal
dpop-htm-mismatch          new, literal
dpop-proof-not-active      new, literal
dpop-refresh-key-mismatch  new, minted twice
dpop-refresh-proof-missing new, minted once
```

`dpop-proof-has-been-used` is deliberately **not** a case: it needs one proof
sent twice, which is a second mint mechanism for one refusal, and
`internal/oidc`'s own test pins it instead.

### Task 5 - the three reasons

`oidc/ciba/poll-pending`, `oidc/ciba/poll-complete` and
`oidc/token/ciba-grant`, rewritten to what §2 measured.

## 4. What is deliberately not done

- The resource-server half of DPoP - `Authorization: DPoP`, `ath`, and the
  `WWW-Authenticate: DPoP algs="…"` challenge. Measured in §1.2, no case wants
  it, filed.
- `dpop_jkt` on the authorization endpoint. Unmeasured here; filed as
  unmeasured rather than left to look decided.
- The 500 at `iat = now-25`.
- Everything CIBA.
