## 1. The allocation exercise

Twenty-six of the description's thirty-one untagged operations were left. Read
off the vendored description with a script rather than counted from prose,
because a counted claim has been wrong every time it was re-counted here:

| family | operations | of them unserved |
|---|---|---|
| the resource server itself | 3 - `GET`, `PUT`, `settings` | 0 |
| `resource` | 9 - `GET`/`POST`, `search`, `{id}` GET/PUT/DELETE, `{id}/attributes`, `{id}/permissions`, `{id}/scopes` | 9 |
| `scope` | 8 - `GET`/`POST`, `search`, `{id}` GET/PUT/DELETE, `{id}/permissions`, `{id}/resources` | 8 |
| `policy` | 5 - `GET`, `POST`, `evaluate`, `search`, `providers` | 4 |
| `permission` | 5 - `GET`, `POST`, `evaluate`, `search`, `providers` | 4 |
| `import` | 1 | 1 |

3 + 9 + 8 + 5 + 5 + 1 = 31, unserved 26. **The brief's twenty-six is right.**
This plan first said 24, from a table built by hand that had dropped
`GET /policy/search` and `GET /permission/search` - a count re-derived from a
summary rather than from the list, which is the exact failure AGENTS.md's
"count from the list, never increment" describes, committed inside the
paragraph that quotes it. The list above is generated from
`internal/conformance/testdata/openapi/keycloak-26.7.1.json`.

**This cut takes the scope family, all eight.** The reasons, in the order they
decided it:

- §1.9 of the first cut's handover swept it, so this cut opens from
  measurements. Re-verifying twelve claims cost one afternoon; measuring the
  resource family from nothing would have cost the cut.
- The resource family is the expensive one and nothing about it is known. Its
  representation is keyed `_id` rather than `id`, it carries an `attributes`
  Java map - so `internal/javamap` is in play, and F95's `model.StringMap`
  question with it - and its listing takes seven query parameters
  (`deep`, `exactName`, `matchingUri`, `name`, `owner`, `scope`, `type`, `uri`)
  where the scope listing takes four. Estimating it from "9 versus 8" is
  exactly the estimate-from-a-count this project has got wrong in some
  direction every time.
- `policy` and `permission` need a policy *provider* model - ten types, each
  with its own configuration - before either `POST` means anything. `evaluate`
  needs the whole evaluation engine. `import` needs all four families first.
  None of them is separable from work this cut is not doing.
- Every operation this cut marks `Implemented` has at least one state
  transition Gloak can actually make. That rules out `GET /resource`,
  `GET /policy` and `GET /permission`, which would be three permanently-`[]`
  handlers: cheap, three parity points, and indistinguishable from a stub.
  `GET /scope/{id}/permissions` and `/resources` are in for the opposite
  reason - they answer `[]` for a scope that exists and an **empty-bodied
  404** for one that does not, and the second half is behaviour Gloak
  reproduces exactly.

Parity: `admin/authz-resource-server` goes 5 of 31 to **13 of 31**.

### F122 belongs in its own branch, and this is why

The brief offered it as "two call sites". It is not, and the reason is a
package boundary rather than an amount of work.

`notifyBackchannel` is a method on `internal/oidc`'s **unexported** `handler`
and it needs four things that live there: `token.Issuer`, the realm's
`keys.RealmKeys`, `h.realmIssuer` and `h.httpClient`. `internal/admin` cannot
call it. Landing F122 means either exporting a seam in `internal/oidc` or
extracting the notifier into a package both can see - and `internal/oidc`,
`internal/token` and `internal/httpx` are all on this branch's do-not-touch
list. The decision is which package owns "tell the other clients", which is a
`Boundaries` table change and deserves to be read on its own.

Filed as such. It stays open, and its urgency is unchanged: an administrator
ending a session still leaves every other client believing the user is signed
in.

## 2. What §1.9 survived, verified rather than transcribed

Twelve claims, re-measured one at a time. **Ten stood, one was true and
incomplete, one was wrong.**

| §1.9 claim | verdict |
|---|---|
| `POST .../scope` with a duplicate name is 201 returning the existing scope, same id | **true and incomplete** - it also *writes* the body's other fields onto the existing scope. `{"name":"alpha","displayName":"changed","iconUri":"http://i"}` against an existing bare `alpha` came back, and read back, with both. It is an upsert, not a lookup-and-echo. |
| no name is a 409 `Duplicate resource error`; `{"name":""}` is a 201 | stands |
| the body's `id` wins | stands, and sharpened: the id is resolved **first**. An id that names nothing plus a name that is taken is a **409**, not an upsert onto the name. |
| the 201 carries no `Location` | stands |
| field order `id, name, iconUri, displayName` | stands - a create sending `name, displayName, iconUri` came back in the other order |
| `{` is `invalid_request`/"Cannot parse the JSON"; empty body is a 500; unknown field is the strict prose shape | stands. `[` is a fourth answer, `unknown_error`/"Cannot parse the JSON", which is AGENTS.md's per-body-shape rule holding. |
| `GET .../scope/{unknown}` is a 404 with an empty body, no `Content-Type`, `Cache-Control: no-cache`; the `PUT` and `DELETE` 404s carry none | stands, and **it omits `X-Frame-Options` too** - see §3 |
| `.../scope/search?name=` is exact, a bare object, 204 on a miss, 400 with an empty body when `name` is absent or empty | stands, and sharpened: exact **and case-sensitive**. `CaseTest` and `casetest` coexist and each matches only itself; `?name=ALPHA` against `alpha` is a 204. |
| the listing's `?name=` is a case-insensitive substring | stands |
| the listing is sorted by name and pages on `first`+`max` | stands, and sharpened twice: the sort is **byte-wise, not case-folded** (`ALPHAX, Bravo, brand-new, charlie`), and **either bound alone pages** - `max=2` alone pages where the role listings ignore it. |
| `PUT` replaces and ignores the body's `id` | stands, both halves |
| `DELETE` success is 204 with no `Cache-Control` | stands |

And one claim from the first cut's §1.4, which this cut had to build against:

- **"`GET .../settings`'s scopes order is neither name order nor insertion
  order and was not pinned" is wrong. It is insertion order.** Four scopes
  created `zulu, yankee, xray, whiskey` - deliberately the reverse of name
  order - came back in exactly that order, while the listing beside them came
  back `whiskey, xray, yankee, zulu`. Deleting `xray` and recreating it moved
  it to the **end**. So one set of scopes has two reads and two orders, and the
  export's is stored rather than computed.
- §1.4's "each entry is stripped of its `id`" is right, and right as stated:
  `iconUri` and `displayName` **are** carried. An earlier probe in this cut
  suggested otherwise and was wrong - the scopes it looked at had had those
  fields removed by an upsert two probes earlier. Re-measured on scopes built
  for the question.

## 3. New measurements

### 3.1 The 409 `Duplicate resource error` does not decide the security headers, and the repository already knew

AGENTS.md's newest security-header exception says **"a 409 `Duplicate resource
error` sends none of the five."** It is false, and the counterexample has been
in this repository since P5.

Measured on one container in one sweep:

| response | five security headers |
|---|---|
| `PUT .../authz/resource-server`, no `decisionStrategy` | **none** |
| `POST .../authz/resource-server/scope`, no `name` | **all five** |
| `PUT .../authz/resource-server/scope/{id}`, no `name` | **none** |
| `PUT /default-default-client-scopes/{id}` repeated | **all five** |
| `POST .../protocol-mappers/models`, no `name` | **none** |
| `POST .../protocol-mappers/models`, duplicate name (`errorMessage` shape) | all five |
| `POST /clients`, `/users`, `/client-scopes`, `/groups`, `/roles` duplicates | all five |

`internal/conformance/testdata/golden/admin/realms-admin/default-default-client-scope-duplicate.http`
is a committed golden of a 409 `Duplicate resource error` **carrying all five**,
and it predates the bullet that says none do.

**The sharpest pair is one path segment and one verb apart.** `POST .../scope`
with `{}` and `PUT .../scope/{id}` with `{}` produce byte-identical bodies from
identical requests - same Content-Type, same realm, same resource server - and
disagree on all five headers. Both causes of the `PUT`'s 409 agree with each
other (an absent name and a name another scope holds), and both causes of the
`POST`'s do too, so it is decided per **verb on an endpoint** and not by the
body, the cause or the status.

The first cut's explanation - "the omission belongs to that response shape" -
is the expensive kind: a correct observation about two endpoints with a wrong
rule attached. `writeDuplicateResource` is right for the two call sites it has
and must not grow a third.

### 3.2 `X-Frame-Options` on an empty-bodied 404 follows the request's `Content-Type`

AGENTS.md records this rule for a **204**: "a 204 carries `X-Frame-Options`
only when the request declared an `application/*` `Content-Type`", measured
across seven values on one endpoint, and `httpx.WriteNoContent` is named as the
one place that decides. The scope family has empty-bodied **404**s and they
follow the same rule:

```
GET    /scope/{unknown}   no Content-Type          no X-Frame-Options
GET    /scope/{unknown}   Content-Type: text/plain no X-Frame-Options
GET    /scope/{unknown}   application/json         X-Frame-Options
DELETE /scope/{unknown}   no Content-Type          no X-Frame-Options
DELETE /scope/{unknown}   application/json         X-Frame-Options
PUT    /scope/{unknown}   application/json         X-Frame-Options
```

So the variable is the **empty body**, not the 204. The four gate refusals and
every JSON error on the family carry all five whatever the request declared,
because they have bodies. That does not make the exception disappear - it moves
it from "a 204" to "a response with no body", which is a wider claim and a
falsifiable one.

### 3.3 The gate covers all eight scope routes, and a bad `first` is a fifth producer of the 404

The brief's open question. Measured on a client without
`authorizationServicesEnabled`, on all eight scope routes, with a caller
holding `manage-authorization` and a caller holding no admin role: every one is
`404 {"error":"HTTP 404 Not Found"}`, identically. So the family shares one
gate and it runs before authorization, exactly as the first cut measured on the
resource server.

New: **`GET .../scope?first=abc` is `404 {"error":"HTTP 404 Not Found"}`** on a
resource server that exists, to a caller who may read it. A query parameter the
description types as `integer` that does not parse makes the route not match.
That body already had three producers - an unmatched path, a wrong verb on a
known path, and a switched-off resource; a query parameter that cannot bind is
a fourth. Gloak's `strconv.Atoi` path must reproduce it.

### 3.4 The role sets are the first cut's, exactly

Swept one single role at a time, seven callers, eleven routes:

| | opened by |
|---|---|
| `GET /scope`, `GET /scope/{id}`, `GET /scope/search`, `GET /scope/{id}/permissions`, `GET /scope/{id}/resources` | `view-authorization`, `manage-authorization`, `view-clients`, `manage-clients` |
| `POST /scope`, `PUT /scope/{id}`, `DELETE /scope/{id}` | `manage-authorization`, `manage-clients` |

`query-clients` and `manage-realm` are 403 on every one, as on the resource
server. So `authzReadRoles` and `authzWriteRoles` are reusable here and are not
re-derived - but they were re-measured, because a role set carried over from a
neighbouring family has been wrong four times in this repository.

**The role check precedes the scope lookup**: a `view-authorization` caller
deleting a scope that does not exist gets 403, and a `manage-authorization`
caller gets 404.

### 3.5 The orderings

`PUT .../scope/{id}`: strict decode, then the scope lookup, then the name
checks. An unknown field addressed to a scope that does not exist is the strict
400; `{"name":"x"}` addressed to it is the empty 404; `{}` addressed to a scope
that *does* exist is the 409.

`POST .../scope`: strict decode, then the id lookup, then the name. `{"zzz":1}`
- unknown field and no name at once - is the strict 400, so the decode precedes
the 409 exactly as it does on `PUT .../authz/resource-server`.

### 3.6 Everything else the family answers

```
GET  /scope                200 application/json;charset=UTF-8, Cache-Control: no-cache
                           sorted by name byte-wise; ?name= case-insensitive substring;
                           ?scopeId= exact and ANDed with ?name=; ?first= and ?max=
                           each page alone; ?first=100 and ?max=0 are []; an empty
                           ?name= and ?scopeId= do not filter
POST /scope                201, Cache-Control: no-cache, charset, no Location
                           upsert by id when the body has one, else by name
                           Content-Type: text/plain is 415; no Content-Type at all is 201
GET  /scope/search?name=   200 bare object / 204 on a miss / 400 empty body when
                           name is absent or empty; all three Cache-Control: no-cache
GET  /scope/{id}           200 charset, no-cache; 404 empty body, no Content-Type, no-cache
PUT  /scope/{id}           204 no Cache-Control; 404 empty body no Cache-Control;
                           409 with no security headers; replaces; ignores the body's id
DELETE /scope/{id}         204 no Cache-Control; 404 empty body no Cache-Control
GET  /scope/{id}/permissions   200 [] charset no-cache; 404 empty on an unknown scope
GET  /scope/{id}/resources     200 [] charset no-cache; 404 empty on an unknown scope
```

A scope is addressed within its resource server: rs1's scope id read through
rs2 is a 404, and `alpha` exists independently in both. A scope `id` is a free
string, not a UUID - `{"id":"zzz"}` is a 201.

## 4. Design

### 4.1 Store: migration `0020_authz_scope.sql`, byte-identical per driver

```sql
CREATE TABLE authz_scope (
    id                 TEXT PRIMARY KEY,
    resource_server_id TEXT NOT NULL REFERENCES authz_resource_server (client_id) ON DELETE CASCADE,
    name               TEXT NOT NULL,
    icon_uri           TEXT NOT NULL,
    display_name       TEXT NOT NULL,
    ordinal            INTEGER NOT NULL,
    UNIQUE (resource_server_id, name)
);
```

`ON DELETE CASCADE` onto `authz_resource_server(client_id)`, which is itself
cascaded from `client`: turning the flag off destroys the settings, measured,
and it has to destroy the scopes with them.

`ordinal` is the settings export's order and exists for the same reason
`realm_default_client_scope.ordinal` does - the order is reproducible and
measured, so it is stored and served rather than masked. Assigned
`COALESCE(MAX(ordinal), -1) + 1` per resource server, which is what
`putRealmDefaultClientScope` already does.

The unique constraint is on `(resource_server_id, name)` and not on `name`,
measured: `alpha` exists in two resource servers at once.

`AuthzRepo` grows six methods rather than gaining a repository of its own,
because a scope has no life outside its resource server and `Authz()` is
already the accessor:

```go
CreateScope(ctx, *model.AuthzScope) error
UpdateScope(ctx, *model.AuthzScope) error
DeleteScope(ctx, clientID, scopeID string) error
ScopeByID(ctx, clientID, scopeID string) (*model.AuthzScope, error)
ScopeByName(ctx, clientID, name string) (*model.AuthzScope, error)
ListScopes(ctx, clientID string) ([]*model.AuthzScope, error)
```

`ListScopes` returns **insertion order**. The four filters, the sort and the
paging run in `internal/admin`, which is `OrganizationRepo`'s stated precedent
and which is what lets the two reads of one set have two orders without two
queries.

### 4.2 `internal/admin/authzscope.go`

Eight handlers behind `guardAuthz`, with `authzReadRoles` on the five reads and
`authzWriteRoles` on the three writes.

Three things that are *not* shared and the measurement that says so for each:

- **The `POST`'s 409 keeps the five security headers and the `PUT`'s drops
  them.** `writeDuplicateResource` stays what it is; the create gets a plain
  `httpx.WriteOAuthError`. §3.1.
- **`authzScopeRepresentation` is reused for the listing, the read, the create
  and the search and is *not* reused for the settings export**, which drops
  `id` and keeps the other three. One struct with `omitempty` on `id` gets the
  export right by accident today, because the export's entries are the same
  three fields - so a second type is not added; the export's element is the
  same struct with the id cleared, and a comment says the two bodies were
  measured differing in exactly that.
- **The name check is `strings.Contains(strings.ToLower(...))` on the listing
  and `==` on the search.** Two `name` parameters on one family, two meanings,
  measured.

An empty-bodied non-204 response needs a writer that suppresses `Date` and
applies §3.2's `X-Frame-Options` rule. `httpx.WriteNoContent` does both and is
hard-wired to 204, and `internal/httpx` is not this branch's to change, so
`writeEmptyStatus` goes in `internal/admin` with a comment saying where it
belongs and a follow-up filed. It writes no body, so the divergence
`internal/httpx`'s boundary rule exists to prevent - a second marshaller - is
not reachable through it.

## 6. What could go wrong

- **The two-orders design is the thing to test.** A `ListScopes` that returned
  sorted rows would make the listing right and the export wrong, and the export
  is the only case that can see it - so the settings case must be recorded
  against a resource server holding scopes created out of name order. A fixture
  that creates them alphabetically passes both implementations.
- **`writeDuplicateResource` growing a third call site** is the mutation this
  cut most expects to survive if the case set is thin. The `POST` and `PUT`
  409s need one case each, and they must assert the headers in **both**
  directions - `AssertHeaders` on one and `AssertAbsentHeaders` on the other -
  or one golden proves nothing.
- **`X-Frame-Options` on the empty 404** is invisible unless a case sends a
  `Content-Type` and another does not. Two cases, one rule.
- A golden holding a per-request value cannot be `Recorded`. None here does:
  every response on this family is a function of the fixture and the request.
