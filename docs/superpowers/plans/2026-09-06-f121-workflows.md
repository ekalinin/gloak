# F121: the `Workflows` tag

Nine operations. Measured against a live Keycloak 26.7.1 on container `kc-wf`
(port 8177) on 2026-09-06, before any design.

The entry says "nine operations answering `application/yaml`, chunked, so this
is a decision about `internal/httpx` before it is nine handlers". The first
three sections are the three questions that decision needs, answered from the
wire. Two of the three came back different from what the entry says.

---

## 1. How many of the nine answer YAML

**Two.** Not nine.

Counted from the vendored description's response content types, then measured:

```
                                          declared responses     measured default
GET    /workflows                         yaml, json             application/yaml;charset=UTF-8
GET    /workflows/{id}                    yaml, json             application/yaml;charset=UTF-8
GET    /workflows/scheduled/{resource-id} json                   application/json;charset=UTF-8
POST   /workflows                         201, no content        201, no body, no Content-Type
PUT    /workflows/{id}                    204, no content        204
DELETE /workflows/{id}                    204, no content        204
POST   /workflows/migrate                 204, no content        204
POST   /workflows/{id}/activate/...       204, no content        204
POST   /workflows/{id}/deactivate/...     204, no content        204
```

So the tag is **two YAML reads, one JSON read and six responses with no body at
all**. `POST /workflows` and `PUT /workflows/{id}` *consume* `application/yaml`,
which is where the other two occurrences of the media type in the description
live, and reading the count off the description without separating request from
response is how "nine" was arrived at.

The reads are content-negotiated and YAML is the server's preference:

```
Accept: (absent)                            application/yaml;charset=UTF-8
Accept: */*                                 application/yaml;charset=UTF-8
Accept: text/html                           application/yaml;charset=UTF-8
Accept: text/plain                          application/yaml;charset=UTF-8
Accept: application/json, application/yaml  application/yaml;charset=UTF-8
Accept: application/json                    application/json;charset=UTF-8
Accept: application/yaml;q=0.5, application/json   application/json;charset=UTF-8
```

`GET /workflows/scheduled/{resource-id}` is JSON only and answers
`Accept: application/yaml` with **406** and `{"error":"HTTP 406 Not Acceptable"}` -
a body the fallback family has not held before.

**A second measurement contradicts AGENTS.md in the same breath.** The YAML 200
carries **four** security headers, not five: `X-Frame-Options` is absent. The
JSON 200 **on the same route, same status, same caller, differing only in
`Accept`** carries all five. That is not a fact about the workflow chapter; it
is the sharpest available data point on a rule AGENTS.md says is unsettled, and
section 4 below is where it goes.

## 2. Whether a library reproduces Keycloak's bytes

**No. A purpose-built emitter, for four reasons, three of which no option in
the library can change.**

The measured body of `GET /admin/realms/master/workflows` with one workflow, read
with `od -c`, is 182 bytes:

```
---
- id: "61ad9536-3e7b-454e-ba51-b101ed3a475a"
  name: "t"
  "on": "user-created"
  steps:
  - uses: "disable-user"
    after: "P5D"
    id: "c3bd4e19-a543-4db6-84d7-905cdb4bfcd8"
```

with a trailing newline, sent chunked with no `Content-Length`.

`gopkg.in/yaml.v3 v3.0.1` is already in `go.mod` as an indirect requirement, so
the dependency itself is free. It was measured four ways in
`tmp-probe/yamlexp` (scratch, not committed), against those exact bytes:

| encoded from | `SetIndent(2)` | `SetIndent(4)` |
| --- | --- | --- |
| a Go struct with yaml tags | differs | differs |
| a hand-built `yaml.Node` tree | differs | differs |
| **the measured bytes, parsed and re-emitted** | **differs** | - |

The last row is the control. Hand the library its own target and ask it to give
it back, and it does not.

The four differences:

1. **No `---`.** yaml.v3 emits a document-start marker only when there is more
   than one document. There is no option for it.
2. **The nested sequence is indented one level too far.** Keycloak puts the
   `-` of `steps:` at the parent mapping's key column; yaml.v3 puts it at
   key column + indent. `SetIndent` moves the mapping indent and the sequence
   indent together and cannot separate them - `SetIndent(2)` and `SetIndent(4)`
   produced byte-identical output on this shape.
3. **Scalars are plain.** Keycloak double-quotes every string and leaves
   integers bare (`batch-size: 25`). yaml.v3 quotes nothing by default; forcing
   it needs a `yaml.Node` tree with `DoubleQuotedStyle` on every scalar, which is
   solvable but is already most of an emitter.
4. **`on` is not quoted.** Keycloak writes `"on": "user-created"`, because
   SnakeYAML is YAML 1.1 where `on` is a boolean and a bare `on` key would
   round-trip as `true`. yaml.v3 is YAML 1.2, does not consider `on` special, and
   emits it bare - visible in the node row above, where the reparse row keeps the
   quotes only because the parser recorded the style it read.

Only (3) and (4) are reachable through the library's API, and reaching them means
building the tree by hand anyway. (1) and (2) are not reachable at all.

This is `internal/javamap`'s situation one layer up: a Java library's output
shape that a Go library will not produce, small enough and closed enough to model
directly. The representation is a twelve-field struct with one nested six-field
struct, and the emitter is a walk over an ordered key list - not a general YAML
writer. It goes in `internal/httpx` beside `writeJSON`, because AGENTS.md's rule
is that `internal/httpx` owns every response body this project writes and a
second format that formatted itself somewhere else would be that rule's second
violation.

**What is deliberately not built**: a YAML *parser*. `POST` and `PUT` consume
`application/yaml`, and a request body is not an observable - nothing in the
conformance contract measures how Gloak reads one. Section 6 says what that costs.

## 3. What a default realm holds, and what a created workflow looks like

**Nothing, and the empty state is `--- []` with a trailing newline** - seven
bytes, on `master` and on a realm created through `POST /admin/realms` alike.
Unlike `attack-detection`, the writes are reachable, so the chapter is not only
its empty state.

The tag is **not gated**: no feature flag, no preview profile, no 404 on a stock
`start-dev` container. AGENTS.md's "not gated by `organizationsEnabled`" holds.

A minimum create is

```yaml
name: t
on: user-created
steps:
  - uses: disable-user
    after: P5D
```

`POST` answers **201**, an empty body, **no `Content-Type` at all**, and an
absolute `Location` ending in a server-minted UUID - a twenty-second uuid tail for
AGENTS.md's create list. The read shape is section 2's body.

Measured vocabulary, from `GET /admin/serverinfo`'s provider list rather than
guessed:

```
workflow-event   client-created  user-authenticated  user-created  client-authenticated
                 user-group-membership-added  user-group-membership-removed
                 user-role-granted  user-role-revoked
                 user-federated-identity-added  user-federated-identity-removed
workflow-step    add-required-action  delete-client  delete-user  disable-client
                 disable-user  grant-role  join-group  leave-group  notify-user
                 remove-required-action  remove-user-attribute  restart  revoke-role
                 set-user-attribute  unlink-user
workflow-condition  has-identity-provider-link  has-role  has-user-attribute  is-member-of
```

Measured behaviours:

```
listing order         sorted by name, ASCII; zzz/aaa/mmm added in that order
                      came back aaa, mmm, zzz, so no Unordered mask
search                case-insensitive substring; exact=true makes it equality
first / max           either bound alone pages - neither the role listings' rule
                      nor the user listing's
max=abc               404 {"error":"HTTP 404 Not Found"}, the malformed-integer
                      producer AGENTS.md already records
includeId=false       drops `id` at both levels - the workflow's and each step's
after                 an ISO-8601 duration; "5 days", "5d", "5" are all 400
name                  unique per realm; a repeat is 400 errorMessage
{type}                an uppercase enum: USERS and CLIENTS route, everything else
                      including `users` is 404 {"error":"HTTP 404 Not Found"}
scheduled steps       gain `scheduled-at` (epoch millis) and `status: "PENDING"`
migrate               from and to are step ids; either alone is 400
enabled: false        400 "Cannot parse the JSON" - a schema field the
                      deserialiser refuses
with:                 accepted and not echoed back
unknown realm         404 {"error":"Realm not found."}
Cache-Control         absent on all nine
```

**The guard is a shape this project has not met.** Every one of the twenty-one
`master-realm` admin roles is 403 on every one of the nine, held singly; so are
`view-realm`+`view-users`, `manage-realm`+`manage-users`, six held together, and
**all twenty-one held together plus `create-realm`** - which is exactly the
composite closure of the realm role `admin`. Holding `admin` itself is 200/201/204,
and removing it again is 403 again. Controls (`GET /users`, `GET /admin/realms`)
flipped with the assignment in every row, so the sweep was not measuring itself.

The guard is therefore **the realm role `admin`, by name, not by what it confers**.

## 4. What this changes in `internal/httpx`

Two things, and the second is a bug this chapter happens to expose.

### `WriteYAML`

A third writer beside `WriteJSON` and `WriteNoContent`, with its own serialiser.
The serialiser is not general: it takes an ordered list of key/value pairs and
knows four value kinds - a quoted string, a bare integer, a nested mapping and a
sequence of mappings - because that is what the representation has.

The rules it encodes, each measured:

- a leading `---\n`
- two-space mapping indent
- a sequence's `-` at the parent key's column, its continuation at + 2
- every string double-quoted, integers bare
- a key double-quoted when YAML 1.1 would resolve it as something other than a
  string, which on this representation is `on` and only `on`
- a trailing newline, which is `writeJSON`'s rule inverted and is why this is not
  a parameter on the existing writer
- `Content-Type: application/yaml;charset=UTF-8`
- **four security headers**: `X-Frame-Options` deleted, as
  `SetUserinfoSecurityHeaders` does

### `WriteNoContent`'s media-type test is wrong

`WriteNoContent` decides `X-Frame-Options` with
`strings.HasPrefix(ct, "application/")`. `application/yaml` has that prefix and
Keycloak sends no `X-Frame-Options` for it, so `PUT /workflows/{id}` would
diverge on its first request.

Measured on `DELETE /admin/realms/master/users/{id}`, a 204 on an endpoint that
consumes nothing, one fresh user per row so the status is 204 every time:

```
application/json                    XFO
application/xml                     XFO
application/x-www-form-urlencoded   XFO
application/yaml                    no XFO
application/yaml;charset=UTF-8      no XFO
application/octet-stream            no XFO
application/pdf                     no XFO
application/ld+json                 no XFO
text/plain                          no XFO
(absent)                            no XFO
```

`application/json` in the same run is the control that differs. The rule is an
**allow-list of three exact media types**, not a prefix and not a `+json` suffix;
`application/ld+json` is what rules the suffix out. The parameters are ignored,
which `application/yaml;charset=UTF-8` and AGENTS.md's already-recorded
`application/json;charset=UTF-8` agree on from opposite sides.

This is not a workflows fix. It is a fix to a rule that has been wrong since P2
for every media type nothing had sent, and this chapter is the first caller that
sends one.

## 5. The build

1. `internal/httpx/yaml.go` - the emitter and `WriteYAML`, with the measured
   bytes as table-driven tests; `errors.go`'s `WriteNoContent` corrected in the
   same commit as its own test.
2. `internal/model` - `WorkflowRepresentation` and `WorkflowStepRepresentation`,
   field order as the description declares it, which is the order the wire has.
3. `internal/store` - migration `0036_workflows`, two tables (a workflow and its
   ordered steps) and a third for a scheduled step, with both drivers.
4. `internal/admin/workflows.go` - the nine handlers, guarded on the realm role
   `admin`.
5. `internal/conformance` - catalogue entries appended at the end of
   `catalog_admin.go`, fixtures appended at the end of `fixture.go`, goldens
   recorded from a live 26.7.1 by `make record`.

## 6. What is not built, and why it is said here rather than found later

- **The `on` expression grammar.** Keycloak parses it with ANTLR and reports
  `Invalid expression: user.create / Error at line 1:5 - extraneous input
  'create' expecting <EOF>`. Gloak accepts the expression as an opaque string and
  validates it against the measured event provider ids. Any request whose
  expression is a compound one gets a different error body than Keycloak's, and
  no golden covers that because no catalogue case sends one.
- **A YAML reader.** `POST` and `PUT` accept `application/json` bodies and the
  subset of `application/yaml` the fixtures send. The subset is written down in
  the parser's doc comment rather than implied.
- **Execution.** Nothing schedules, runs or migrates a step. `activate` records a
  scheduled step so `scheduled/{resource-id}` can answer it; `migrate` validates
  its two ids and answers 204. The observable is the answer, and the answer is
  what is reproduced.
