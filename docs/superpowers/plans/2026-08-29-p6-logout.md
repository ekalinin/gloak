# P6's first cut: the RP-initiated logout endpoint

Date: 2026-08-29
Measured against: a live Keycloak 26.7.1, container `kc-p6` on 8092
Follows: `docs/superpowers/plans/2026-08-29-p3-serve-auth.md`

`GET`/`POST /realms/{realm}/protocol/openid-connect/logout` becomes a route.
Everything in it is measured first; nothing in this plan was written from the
catalogue's expectations, and section 1 says why that mattered more here than it
usually does.

## 1. How much of this endpoint is reachable, and is the cut worth its container?

The brief predicted the meter would move by one, from the one `Recorded` case
the chapter carries. **It is worth more than that, and the reason is that the
chapter's five cases are not the endpoint.** The `oidc/logout` chapter describes
one verb and one shape. The endpoint has two verbs, two request families per
verb, four response families, and a validation order nobody has written down.

Measured, the endpoint answers with exactly six shapes:

| # | Shape | Reached by | Gloak can serve it |
|---|---|---|---|
| 1 | **302** to `post_logout_redirect_uri`, `Cache-Control: no-cache` | a validated logout | **yes, byte for byte** |
| 2 | **400** theme error page | three distinct rejections | envelope only, body is P13 |
| 3 | **200** theme `Logging out` confirmation page | no hint and no redirect target | envelope only, body is P13 |
| 4 | **200** theme `You are logged out` page | a valid hint and no redirect target | envelope only, body is P13 |
| 5 | **204** empty | `POST` carrying a `refresh_token` | **yes, byte for byte** |
| 6 | **400**/**401** JSON | the `POST` family's rejections | **yes, byte for byte** |

Shapes 1, 5 and 6 are four fifths of the endpoint's branches and every one of
them is servable today. Shapes 2, 3 and 4 are theme pages whose bodies carry the
per-container `/resources/<hash>/` segment P3 already parked, so their goldens
stay `Pending` for the same reason P3's two do - **and their envelopes are
served anyway**, because the envelope is measured, stable, and is what a client
actually branches on.

The second thing section 1 has to answer is whether the one `Recorded` case can
be promoted, and the honest answer is **not as it stands**. Its fixture is
`browser-logged-in`, which drives Keycloak's login form; `authorizeStep`
requires a 200 and Gloak answers `/auth` with the 400 page, so the fixture
cannot run against Gloak and `TestConformance` skips the case forever. The case
would sit at `Recorded` with the endpoint fully served.

Measured 2026-08-29, that is fixable without weakening the case:

```
direct grant on p6-a, no cookie jar at all, then
GET /logout?id_token_hint=<id token>&post_logout_redirect_uri=...&state=bye

HTTP/1.1 302
Location: http://localhost:9999/callback?state=bye
Cache-Control: no-cache
Set-Cookie: AUTH_SESSION_ID=...
sec present=[Referrer-Policy, Strict-Transport-Security, X-Content-Type-Options, X-Robots-Tag]
sec absent=[X-Frame-Options, Content-Security-Policy]
```

Byte for byte the browser fixture's response, minus the two cookie clears -
which the case masks as volatile and does not assert. **So the case moves to a
direct-grant fixture and is promoted.** What is lost is written down in the
handover rather than silently dropped: nothing now measures that a browser
session's `KEYCLOAK_IDENTITY` and `KEYCLOAK_SESSION` are cleared with
`Max-Age=0`, because Gloak has no browser session cookie to clear. That is a
follow-up, not a regression.

**The cut is worth its container.** Section 2 is what it bought.

## 2. What was measured, 2026-08-29, container `kc-p6` on 8092

Sixty-odd probes across eleven scripts, each printing the argv it then executed.
The full transcript goes to `docs/superpowers/handover/p6-logout.md`; what the
implementation rests on is here.

### 2.1 Three claims in AGENTS.md about this endpoint, re-verified

The brief named three and asked for each to be re-verified rather than
inherited. **Two of the three are false as written.**

**"Logout without an `id_token_hint` does not redirect. It serves the theme's
`Logging out` confirmation page, 200, whatever the `post_logout_redirect_uri`
is."** False. The redirect happens whenever there is no browser session to
confirm:

```
no cookie jar, GET /logout?client_id=p6-a&post_logout_redirect_uri=http://localhost:9999/callback
  302  Location: http://localhost:9999/callback

with a live browser session, the same request
  200  the Logging out page, "Do you want to log out?"
```

The confirmation page is not "what a hintless logout answers". It is what a
logout answers when it has a session to end and no authority to end it without
asking. Without a session there is nothing to confirm, so it redirects. The
earlier measurement was taken through a cookie jar and read the session for the
parameter.

**"`post.logout.redirect.uris` is a separate client attribute. A client whose
`redirect_uri` validates at the authorization endpoint is still refused at the
logout endpoint until it is set."** False in its second sentence. `p6-b`
registers `redirectUris` and **no** `post.logout.redirect.uris` at all, and its
own registered redirect URI validates at the logout endpoint:

```
p6-b, no post.logout.redirect.uris, GET /logout with its redirectUris entry
  302  Location: http://localhost:9998/callback
```

Measured across four attribute values, the attribute is a *filter* over
`redirectUris` rather than a separate registration:

| `post.logout.redirect.uris` | Accepted targets |
|---|---|
| absent | the client's `redirectUris` |
| `""` | the client's `redirectUris` |
| `"+"` | the client's `redirectUris` |
| `"-"` | **nothing**; every target is `Invalid redirect uri` |
| anything else | that `##`-separated list, and **not** `redirectUris` |

`p6-c` sets `+` and accepts its `redirectUris` entry and refuses a sibling path.
`p6-minus` sets `-` and refuses its own `redirectUris` entry. `p6-e` sets
`http://localhost:9995/cb*##http://localhost:9995/exact` and accepts `/cb`,
`/cbxyz`, `/cb?x=1` and `/exact`, and refuses `/callback` and `/CB`.

**"Its successful redirect carries `state` and nothing else - no `iss` - and
`Cache-Control: no-cache`."** True, and re-confirmed on both fixtures. One
qualification the sentence does not carry, and it is the opposite of `/auth`:

```
/auth   state=  ->  the redirect carries state=      (an empty value is echoed)
/logout state=  ->  the redirect carries no state at all
```

### 2.2 The rejection order, pinned by driving two faults at once

Twelve paired requests, each pair deciding one adjacency:

```
1  realm                404 {"error":"Realm does not exist"}   JSON, not a page
2  id_token_hint        400 page "Invalid parameter: id_token_hint"
3  post_logout_redirect_uri  400 page "Invalid redirect uri"
   ...or 400 page "Missing parameters: id_token_hint" when neither
      id_token_hint nor client_id was sent at all
--- everything below succeeds ---
4  a redirect target    302
5  no redirect target   200 page
```

Step 2 before step 3 is the surprise, and it is measured both ways round: a
garbage hint with an *unregistered* URI answers about the hint, and a *good*
hint with an unregistered URI answers about the URI. So the hint is not merely
checked first, it is checked before the URI is looked at.

Step 2 covers more than a malformed token. All four of these are
`Invalid parameter: id_token_hint`:

- rubbish that is not a JWT
- an access token or a refresh token in the hint's place
- a hint whose signature does not verify, or whose payload was rewritten
- **a hint whose `azp` disagrees with the `client_id` parameter sent beside it**
- a hint issued by another realm

And two things that look like they belong in step 2 and do not:

- **An expired `id_token_hint` is accepted.** A client pinned to
  `access.token.lifespan=1`, waited out, still logs out and still redirects.
  RFC-wise the OP may accept one; measured, this one does.
- **A hint naming a session that is already gone is accepted.** The same hint
  twice answers 302 twice.

A hint whose client has since been **deleted** answers `Invalid redirect uri`,
not `Invalid parameter: id_token_hint` - the token verifies against the realm
key, and it is the redirect URI that then has no client to validate against.

**A rejected logout ends nothing.** After every 400 above, the session's refresh
token still works. Validation completes before anything is destroyed.

### 2.3 The `POST` family

`POST` reads the **body and not the query**, exactly as `/auth` does: the same
parameters on the query string answer the confirmation page.

The presence of `refresh_token` in the body decides which family the request is
in. With one, the request is client-authenticated and answers 204; without one,
it falls through to the `GET` families - a `POST` carrying `client_id` and a
registered `post_logout_redirect_uri` answers the same 302.

```
POST client_id + refresh_token                     204, no body, Cache-Control: no-cache
POST the same refresh_token again                  204            (idempotent)
POST client_id + refresh_token + a redirect uri    204            (the uri is ignored)
POST refresh_token + id_token_hint                 204            (refresh_token wins)
POST garbage refresh_token                         400 {"error":"invalid_grant",
                                                        "error_description":"Invalid refresh token"}
POST an access token as the refresh_token          400 the same
POST an id_token as the refresh_token              400 the same
POST another client's refresh_token                400 {"error":"invalid_grant",
                                                        "error_description":"Invalid refresh token. Token client and authorized client don't match"}
POST refresh_token with no client_id               401 {"error":"invalid_client",...}
POST confidential client, no secret                401 {"error":"unauthorized_client",...}
POST confidential client with the secret           204
```

The last two are the `invalid_client`/`unauthorized_client` split AGENTS.md
already records, holding on a fourth endpoint.

### 2.4 Header sets, per response family

```
                          CC          RP HS XC XF XR CSP  Content-Type
302 redirect              no-cache     Y  Y  Y  .  Y  .   none, empty body
400 theme error page      no-cache     Y  Y  Y  Y  Y  Y   text/html;charset=utf-8
200 theme page (both)     no-cache     Y  Y  Y  Y  Y  Y   text/html;charset=utf-8
204 POST success          no-cache     Y  Y  Y  Y  Y  Y   none, empty body
400/401 POST JSON         none         Y  Y  Y  Y  Y  .   application/json
404 realm                 none         -  -  -  -  -  -   application/json
```

Two of these contradict a neighbour that looks identical.

**`/logout`'s 400 page carries `Cache-Control: no-cache`; `/auth`'s 400 page
carries none.** Measured side by side on one container in one script. So
`httpx.WriteThemeErrorPage` cannot be reused unchanged, and "add a
`Cache-Control` for consistency" would break `/auth` exactly as its own doc
comment warns.

**The 302 omits `X-Frame-Options` and `Content-Security-Policy`**, which is what
the observed document already predicted from `/auth`, now confirmed on the
second endpoint that redirects a browser to a client's registered URI.

**The 204 carries `Content-Security-Policy`.** That is a second protocol
response carrying it, beside revocation's success.

Cookies, per family: the 302 and both 200 pages issue a fresh `AUTH_SESSION_ID`;
the 400 page and the 204 issue none. A browser session's `KEYCLOAK_IDENTITY` and
`KEYCLOAK_SESSION` are cleared with `Max-Age=0` on the 302 only when they were
sent.

### 2.5 The verbs

```
GET      the families above
POST     the families above
HEAD     behaves as GET - 302 with the Location, or 200 with the page's headers
OPTIONS  200, empty, and **no Allow header**
PUT      405 {"error":"HTTP 405 Method Not Allowed"}, no Allow header
DELETE   405 the same
PATCH    405 the same
```

Two things here are new and neither is acted on in this cut.

**The 405 body is measured for the first time.** AGENTS.md records that `/auth`
answers `PUT`, `DELETE` and `PATCH` with "a real 405 with `application/json`"
and does not say what is in it. It is `{"error":"HTTP 405 Method Not Allowed"}`,
on both endpoints, re-measured side by side. That is a fifth spelling in the
fallback family and it goes to the handover for F31, not into the router.

**`OPTIONS` disagrees between the two endpoints.** `/auth` answers
`Allow: HEAD, POST, GET, OPTIONS`; `/logout` answers 200 with no `Allow` at all.
Two neighbouring endpoints on one container. This is the fourth data point in
F31's pile and, per AGENTS.md, four data points that disagree still do not say
what the rule is. Gloak keeps answering 404 to all of them.

## 4. Task 1: `internal/httpx`, the two writers

`WriteLogoutRedirect(w, location)`: the 302 with `Cache-Control: no-cache`, the
five security headers minus `X-Frame-Options`, no `Content-Security-Policy`, no
`Content-Type`, no body. It is not `WriteAuthorizationRedirect` with a different
constant because the two differ only in that constant today and a shared writer
taking a `Cache-Control` string would be one call site away from making the
difference invisible.

`WriteThemeErrorPage` gains a `cacheControl string` parameter. `/auth` passes
`""` and keeps sending none; `/logout` passes `"no-cache"`. The alternative -
a second page writer - duplicates the body constant, which is the one thing
`internal/httpx` exists to keep in one place.

`WriteThemePage(w, status, cacheControl)` is **not** added. Shapes 3 and 4 are
200s carrying a body Gloak cannot produce; they reuse the error page writer with
a 200, which is the same envelope decision P3 made and the same placeholder
body.

## 5. Task 2: `internal/token`, `ParseID`

`ParseID` verifies RS256 against the realm's signing key and checks `iss` and
`typ`, and **does not check `exp`**. The expiry omission is the measurement in
section 2.2 and is the whole reason it cannot be `ParseAccess` with a different
type constant.

## 6. Task 3: `internal/oidc/logout.go`

```
resolveRealm                                 -> 404 JSON
read params: query on GET, body on POST
POST and refresh_token present                -> the POST family
  authenticateClient                          -> 401 invalid_client / unauthorized_client
  parse the refresh token                     -> 400 Invalid refresh token
  the token's azp != the authenticated client -> 400 ...Token client and authorized client don't match
  delete the session                          -> 204
otherwise the GET family
  id_token_hint present but unusable          -> 400 page
  id_token_hint and client_id disagree        -> 400 page
  neither present, and a redirect uri was     -> 400 page
  the redirect uri does not validate          -> 400 page
  end the session if a hint named one
  a redirect target                           -> 302
  no redirect target                          -> 200 page
```

The redirect URI comparison is `matchRedirectURI`, unchanged, over the patterns
`postLogoutPatterns` derives from the client. Measured identical to `/auth`'s on
seven probes: exact, non-normalised, case-sensitive, `*` only as a suffix, the
query and fragment cut in the wildcard branch alone.

`backchannel` and `frontchannel` stay `Pending` and their `Reason` is corrected:
the endpoint is implemented now, and what they wait for is a harness that can
observe Keycloak calling *out* to a client.

## 8. Task 5: what is deliberately not done

- **The two theme-page bodies.** P13.
- **`AUTH_SESSION_ID`.** Gloak has no authentication session; minting a cookie
  value would be inventing an observable. Follow-up.
- **The confirmation page's session branch.** Gloak has no browser session
  cookie, so shape 3 and shape 4 are one branch here where Keycloak has two.
  Recorded as a divergence.
- **405 and `OPTIONS`.** F31.
- **Back-channel and front-channel logout.** They need Keycloak to call the
  client, which the harness cannot observe.
