# P13, first cut: the browser login end to end

Gloak validates an authorization request through ten measured checks and then
answers the page family's 400, because Keycloak renders a login page there and
Gloak has none. That is follow-up F50. This cut serves the flow: the login page,
`POST /realms/{realm}/login-actions/authenticate`, and the authorization code
the redirect carries.

**It is the flow, not the theme.** The bodies stay Gloak's placeholder, as
`authorize.go` and `logout.go` already do for their page families. What changes
is that a valid authorization request now ends in a code.

Everything below was measured on 2026-08-30 against
`quay.io/keycloak/keycloak:26.7.1` run as `kc-p13` on port 18194, with two
public clients `p13-a` and `p13-b` registering `http://localhost:9999/callback`
and a second user `p13user`.

> The port matters. The brief named 8094; a parallel stream's `gloak` process was
> bound to `*:8094` on IPv6, `localhost` resolved there first, and the first
> probe run measured **that process** rather than Keycloak - it answered
> `GET /auth` with the unmatched-path 404. Every transcript here is from 18194,
> whose listener was confirmed to be colima's forwarder before anything was
> measured.

## 1. The measured flow

### 1.1 What crosses between the two endpoints

`GET /auth` mints five values and hands three of them to the browser as cookies
and five as query parameters on the login form's `action`.

| Value | Minted | Carried by | Shape |
|---|---|---|---|
| root auth session id | `/auth` | `AUTH_SESSION_ID` cookie | 24 chars base64url (18 bytes) |
| `tab_id` | `/auth`, per request | the form action | 11 chars base64url (8 bytes) |
| `session_code` | `/auth`, per request | the form action | 43 chars base64url (32 bytes) |
| `execution` | the realm, once | the form action | a UUID, **stable across logins in one container** |
| `client_data` | `/auth`, per request | the form action | unpadded base64url JSON |
| auth session hash | `/auth` | `KC_AUTH_SESSION_HASH` cookie | 64 chars standard base64 (48 bytes), **quoted** |
| the restart record | `/auth` | `KC_RESTART` cookie | a `dir`/`A256GCM` JWE |

The action's parameter order is `session_code`, `execution`, `client_id`,
`tab_id`, `client_data`.

**The root auth session id is the `session_state`.** This is the finding the
rest of the design rests on, and it is measured three ways at once:

```
AUTH_SESSION_ID  base64-decodes to  QTmg9gDxlnuFEYSwm6NU0pGO.xT7P9CHNSywfsXif3rv9Lu...
                                    ^^^^^^^^^^^^^^^^^^^^^^^^
login redirect   session_state=     QTmg9gDxlnuFEYSwm6NU0pGO
KEYCLOAK_IDENTITY  "sid":           QTmg9gDxlnuFEYSwm6NU0pGO
authorization code, second part:    QTmg9gDxlnuFEYSwm6NU0pGO
```

So `session_state` is decided **before any credential is seen**. The cookie's
value is `base64(<root id>.<86 chars>)`; the second part is opaque and nothing
observable says what it is.

`client_data` is unpadded base64url of a JSON object whose keys are, in order,
`ru` (the redirect URI), `rt` (the response type), `rm` (the response mode,
**only when one was sent**) and `st` (the state). `st` follows `/auth`'s own
`state` rule exactly: absent when no `state` was sent, present and empty when
`state=` was.

```
{"ru":"http://localhost:9999/callback","rt":"code","st":"xyz123"}
{"ru":"http://localhost:9999/callback","rt":"code","rm":"fragment","st":"xyz123"}
{"ru":"http://localhost:9999/callback","rt":"code"}                 no state sent
{"ru":"http://localhost:9999/callback","rt":"code","st":""}         state= sent
```

**`client_data` is parsed and then ignored.** Measured three ways: a
`client_data` naming `"ru":"http://evil.example/cb"` still redirects to the
registered callback, one naming `"st":"TAMPERED"` still echoes `xyz123`, and one
adding `"rm":"fragment"` still puts the parameters in the query. Dropping it
entirely succeeds. But `client_data=!!!!` is a **400**, so it is parsed. It is a
restart hint, never an authority - reading the redirect URI out of it is the
mistake this measurement exists to prevent.

### 1.2 The success path

`GET /auth`, everything valid: **200**, `text/html;charset=utf-8`,
`Cache-Control: no-store, must-revalidate, max-age=0`, `Content-Language: en`,
`Content-Security-Policy`, all five security headers, and three `Set-Cookie`s in
this order:

```
AUTH_SESSION_ID=<v>;Version=1;Path=/realms/master/;Secure;HttpOnly;SameSite=None
KC_AUTH_SESSION_HASH="<v>";Version=1;Path=/realms/master/;Max-Age=60;Secure;SameSite=None
KC_RESTART=<jwe>;Version=1;Path=/realms/master/;Secure;HttpOnly;SameSite=None
```

The page holds exactly one form, `id="kc-form-login"`, `method="post"`, whose
only inputs are `username` (text, `value=""`), `password` (password,
`value=""`) and `credentialId` (hidden, **no `value` attribute at all**).

`POST /login-actions/authenticate` with the right credentials: **302**, empty
body, `Cache-Control: no-store, must-revalidate, max-age=0`, `Content-Security-Policy`,
**all five security headers including `X-Frame-Options`**, and three
`Set-Cookie`s:

```
KC_RESTART=;Version=1;Path=/realms/master/;Max-Age=0
KEYCLOAK_IDENTITY=<HS512 JWT, typ Serialized-ID>;Version=1;Path=/realms/master/;Secure;HttpOnly;SameSite=None
KEYCLOAK_SESSION=<v>;Version=1;Path=/realms/master/;Max-Age=36000;Secure;SameSite=None
```

`KC_RESTART`'s clear carries neither `Secure` nor `HttpOnly`.
`KEYCLOAK_SESSION`'s value is `KC_AUTH_SESSION_HASH`'s with `+/` rewritten to
`-_`: two cookies, one value, two base64 alphabets. `KEYCLOAK_IDENTITY`'s
payload keys are `exp iat jti iss sub typ sid state_checker`, `typ` is
`Serialized-ID`, and `exp - iat` is 36000.

The `Location`'s query key order is `state`, `session_state`, `iss`, `code`.
The code is three dot-separated parts:

```
0ba8ebcc-2ee3-d389-f193-b4d3c82d25c2 . QTmg9gDxlnuFEYSwm6NU0pGO . df874b59-6214-41e7-89f0-3714318fc015
```

part 1 is laid out like a UUID and is not one - the version nibble measured `d`
and the variant nibble `f` on one sample, `2` and `7` on another. part 2 is the
`session_state`. part 3 is the client's own internal UUID.

`response_mode` is carried through the login from the authentication session,
not from `client_data`: absent and `query` use the query, `fragment` uses the
fragment, and `form_post` answers **200** with the auto-submitting form whose
input order is `code`, `iss`, `state`, `session_state`.

### 1.3 Where the parameters are read from

**`/login-actions/authenticate` reads its five parameters from the query
string only, and its credentials from the body.** Measured: putting all five in
the body with an empty query answers the 400 client page; putting only
`session_code` in the body answers the no-`session_code` page. A `text/plain`
body and an empty body both behave as empty credentials.

That is the exact mirror of `/auth`, which **reads the body and ignores the
query** on a `POST`. One flow, two endpoints, opposite rules.

### 1.4 A repeated parameter is not an error here

`zz` twice, `tab_id` twice, and `session_code` twice with the second value
garbage all **succeed**, first value winning. `/auth` answers `duplicated
parameter` for any key sent twice, including keys it never reads. This is the
second endpoint in the flow to disagree with `/auth` about its own query string.

### 1.5 The rejection order, from paired faults

Each row below is a request carrying two faults at once, and the answer says
which check ran first.

| Fault | Answer |
|---|---|
| `client_data` unparseable | 400 page, `Invalid Request` |
| no cookies at all | 400 page, `Restart login cookie not found. ...` |
| `client_id` absent, empty, unknown or disabled | 400 page, `An error occurred, please login again through your application.` |
| `session_code` wrong, expired or spent | the restart family, see 1.6 |
| `execution` absent or unknown | **200** page, `Page has expired` |
| credentials wrong | **200** login page, `Invalid username or password.` |

The pairs that pin the adjacencies:

```
no client_id     + bad client_data  -> Invalid Request              client_data first
bad client_data  + no cookies       -> Invalid Request              client_data first
unknown client_id+ no cookies       -> Restart login cookie...      cookies before client_id
no client_id     + bad session_code -> An error occurred...         client_id before session_code
bad session_code + bad execution    -> Page has expired             (see below)
bad session_code + wrong password   -> the restart family           session_code before credentials
bad execution    + wrong password   -> Page has expired             execution before credentials
no cookies       + wrong password   -> Restart login cookie...      cookies before credentials
```

So the order is **client_data, cookies, client_id, session_code, execution,
credentials**.

`bad session_code + bad execution` answering the `Page has expired` page rather
than the restart 302 is the one adjacency this cut does not claim to have
explained; it is recorded as measured and served as measured.

### 1.6 The three answers to an unusable authentication session

This is the part the observed document has half of, and getting it wrong is how
a login loop becomes an error page. Measured as a clean grid, spending the code
first and then varying the three cookies independently:

```
AUTH_SESSION_ID  KC_RESTART  KEYCLOAK_IDENTITY  -> outcome
       -              -              -           400 page, Restart login cookie not found
       -              -              Y           302 to the client, temporarily_unavailable
       -              Y              -           302 restart
       -              Y              Y           302 restart
       Y              -              -           400 page, Restart login cookie not found
       Y              -              Y           302 to the client, temporarily_unavailable
       Y              Y              -           302 restart
       Y              Y              Y           302 restart
```

and, with a **valid** session code:

```
AUTH_SESSION_ID=Y, KC_RESTART=-  -> the code            the auth session cookie alone is enough
AUTH_SESSION_ID=-, KC_RESTART=Y  -> 302 restart
AUTH_SESSION_ID=-, KC_RESTART=-  -> 400 page
```

So, in order:

1. `KC_RESTART` present and parseable → **302 restart**, to
   `/realms/{realm}/login-actions/authenticate?client_id&tab_id&client_data`
   with a **freshly minted `tab_id`**, carrying `Content-Security-Policy` and
   `X-Frame-Options`. Following it serves the login page with
   `Your login attempt timed out. Login will start from the beginning.`
2. else `KEYCLOAK_IDENTITY` present → **302 to the client**,
   `error=temporarily_unavailable`, `error_description=authentication_expired`,
   key order `error`, `error_description`, `state`, `iss`.
3. else → **400** theme page, `Restart login cookie not found. It may have
   expired; it may have been deleted or cookies are disabled in your browser.
   If cookies are disabled then enable them. Click Back to Application to login
   again.`

The observed document records only outcome 2, unconditioned, as "replaying a
spent `session_code` does not re-serve anything: it redirects". That is the
**browser** case and it is right for a browser, because the login clears
`KC_RESTART` with `Max-Age=0`. It is wrong as a general statement: a client that
still holds a `KC_RESTART` restarts and does re-serve the login page. An
**empty** `KC_RESTART`, which is what a cleared cookie leaves behind, counts as
absent.

An **expired** `session_code` - measured by setting the realm's
`accessCodeLifespanLogin` to 1 and waiting three seconds - takes exactly the
same three-way branch as a spent one. Expiry and replay are one case, not two.

### 1.7 The credential failures

All of them answer **200** with the login page re-served, `Cache-Control:
no-store, must-revalidate, max-age=0`, and a **rotated `session_code`** while
`execution`, `tab_id` and `client_data` stay the same. Retrying with the rotated
code succeeds.

| Request | Message |
|---|---|
| wrong password | `Invalid username or password.` |
| unknown username | `Invalid username or password.` |
| empty or absent `username` | `Invalid username or password.` |
| empty or absent `password` | `Invalid username or password.` |
| no form fields at all | `Invalid username or password.` |
| a disabled user | `Account is disabled, contact your administrator.` |

The username is echoed back into the form's `value` when one was sent. A
`credentialId` field is not required: omitting it succeeds. The username is
matched case-insensitively - `ADMIN` logs in.

A user carrying a required action answers a **302** to
`/realms/{realm}/login-actions/required-action?execution=UPDATE_PASSWORD&...`,
a fourth endpoint that this cut does not serve.

### 1.8 The verbs, and a sixth data point for F31

Measured side by side on one container:

```
                                    HEAD  OPTIONS  PUT  DELETE  PATCH
/protocol/openid-connect/auth        200    200    405   405     405
/login-actions/authenticate          404    200    405   405     405
```

`OPTIONS` answers `Allow: HEAD, POST, GET, OPTIONS` on both. The 405 body is
`{"error":"HTTP 405 Method Not Allowed"}` with no `Allow`. **`HEAD` is 200 on
`/auth` and 404 on its neighbour in the same flow**, which is one more pair
that disagrees for AGENTS.md's list. An unknown realm on `/login-actions` is
`{"error":"Realm does not exist"}`, the protocol side's spelling.

### 1.9 The theme error page's third `Cache-Control`

```
GET  /auth                        400 and 403 pages   no Cache-Control at all
GET  /logout                      400 page            no-cache
POST /login-actions/authenticate  400 pages           no-store, must-revalidate, max-age=0
```

Measured side by side on one container. `httpx.WriteThemeErrorPage` takes the
value as an argument, and this is the third endpoint to prove that right.

## 2. What Gloak will serve

### 2.1 Storage, and why it is in memory

The authentication session and the authorization code both live in memory,
in `internal/oidc`. That is the faithful model - Keycloak keeps both in
Infinispan caches rather than in the database, because both are short-lived -
and it is also forced here, because `internal/store` belongs to another agent
this session.

It makes this cut **single-process**: two Gloak replicas will not share an
authentication session or a code, where they do share realm signing keys
precisely so that they agree. That is filed as a follow-up with the design, and
said plainly in the pull request body.

The **user** session is not in memory. It goes through the existing
`h.startSession`, which persists it, so the code the login mints names a session
the token endpoint can already find.

### 2.2 New files

- `internal/oidc/authsession.go` - the in-memory authentication session store,
  its tab records, the code store, and the minting of every value in the table
  in 1.1 at its measured length.
- `internal/oidc/loginactions.go` - the handler, the six checks of 1.5 in the
  measured order, and the three-way branch of 1.6.
- `internal/httpx` gains the writers: the login page, the login redirect (which
  is **not** `WriteAuthorizationRedirect` - it keeps `X-Frame-Options` and
  `Content-Security-Policy` where that one drops both), and Keycloak's exact
  cookie spelling.

`internal/httpx` is where the cookie header is written because Keycloak spells
its attributes with no space after the semicolon and with a `Version=1` that
`net/http`'s `http.SetCookie` cannot emit at all. A response header is
observable, so it is a body-formatting decision and it belongs there.

### 2.3 What is deliberately left out

- **The `authorization_code` grant at the token endpoint.** The code is minted
  and stored with everything an exchange needs; redeeming it is eight measured
  rejections and a success body, and it is its own cut. Follow-up.
- **SSO.** Gloak sets `KEYCLOAK_IDENTITY` and does not read it, so a second
  `/auth` on a live browser session serves the login page again where Keycloak
  redirects with a code, and `prompt=none` still answers `login_required`.
  Follow-up.
- **The restart landing page's message** and every other page's prose. The
  envelope is served, the branch is guarded by unit tests, the body is P13's
  later work. This is F67's shape, repeated.
- `/login-actions/required-action`.
