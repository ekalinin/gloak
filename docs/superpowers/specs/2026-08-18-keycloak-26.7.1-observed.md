# Keycloak 26.7.1: observed behaviour

Date: 2026-08-18
Source: `quay.io/keycloak/keycloak:26.7.1`, `start-dev`, default configuration

This document records what was measured on a live instance, not what the
documentation claims. It resolves section 14 of the design spec. Values here are
the contract Gloak has to reproduce.

## Token endpoint response

Fields, in the order Keycloak emits them:

```
access_token, expires_in, refresh_expires_in, refresh_token,
token_type, id_token, not-before-policy, session_state, scope
```

`not-before-policy` is spelled with hyphens, not underscores. `id_token` is present
only when the `openid` scope was requested.

In the `master` realm `expires_in` is 60 and `refresh_expires_in` is 1800.

## Token signing

Access and ID tokens are signed RS256. **Refresh tokens are signed HS512**, with a
different key. This is not a detail that can be skipped: a refresh token is opaque
to clients, so Keycloak signs it symmetrically.

## Claim sets

Access token, ordinary client:

```
acr, allowed-origins, aud, azp, email_verified, exp, iat, iss, jti,
preferred_username, realm_access, resource_access, scope, sid, sub, typ
```

`typ` is `Bearer`. `aud` is an array. `allowed-origins` is a non-standard claim
holding the client's web origins.

ID token:

```
acr, at_hash, aud, azp, email_verified, exp, iat, iss, jti,
preferred_username, sid, sub, typ
```

`typ` is `ID`. `aud` here is a **string**, not an array.

Refresh token:

```
aud, aud_x, azp, exp, iat, iss, jti, prov, scope, sid, sub, typ
```

`typ` is `Refresh`. `aud` is the issuer URL. `aud_x` carries what the access token
puts in `aud`. `prov` is `default`. The `scope` string is the full internal scope
list (`openid email acr roles basic service_account web-origins profile`), which
differs from the access token's shorter `scope` (`openid email profile`).

`jti` on access tokens carries an instance prefix, for example
`onrtro:13f91f50-6b34-71c7-6d86-d201ef27be67`. ID and refresh tokens use a plain
UUID. This is a normalisation target for golden tests.

## Lightweight access tokens

The `admin-cli` client ships with
`client.use.lightweight.access.token.enabled = true`. Its access tokens therefore
carry only:

```
azp, exp, iat, iss, jti, scope, sid, typ
```

No `sub`, no `aud`, no `realm_access`. Any bootstrap that creates `admin-cli`
without this attribute will produce tokens that do not match the original.

## Password hashing

The default for a bootstrapped admin user:

```json
{
  "hashIterations": 5,
  "algorithm": "argon2",
  "additionalParameters": {
    "hashLength": ["32"],
    "memory": ["7168"],
    "type": ["id"],
    "version": ["1.3"],
    "parallelism": ["1"]
  }
}
```

Argon2id, version 1.3, 5 iterations, 7168 KiB of memory, parallelism 1, 32-byte
output. Note that the parameter values are arrays of strings.

## Error formats

There are **four** distinct shapes, not two. This is the single most important
finding in this document.

**Shape 1, RFC 6749 on the token endpoint:**

| Case | Status | Body |
|---|---|---|
| wrong password | 400 | `{"error":"invalid_grant","error_description":"Invalid user credentials"}` |
| unknown client | 401 | `{"error":"invalid_client","error_description":"Invalid client or Invalid client credentials"}` |
| wrong client secret | 401 | `{"error":"unauthorized_client","error_description":"Invalid client or Invalid client credentials"}` |
| missing `grant_type` | 400 | `{"error":"invalid_request","error_description":"Missing form parameter: grant_type"}` |
| unknown `grant_type` | 400 | `{"error":"unsupported_grant_type","error_description":"Unsupported grant_type"}` |
| bad or replayed code | 400 | `{"error":"invalid_grant","error_description":"Code not valid"}` |
| bad refresh token | 400 | `{"error":"invalid_grant","error_description":"Invalid refresh token"}` |

An unknown client and a wrong secret return **different error codes** with identical
descriptions. A replayed authorization code is indistinguishable from a fabricated
one.

**Shape 2, bare `error` with a human message:**

| Case | Status | Body |
|---|---|---|
| discovery for unknown realm | 404 | `{"error":"Realm does not exist"}` |
| admin API, unknown realm | 404 | `{"error":"Realm not found."}` |
| admin API, unknown user | 404 | `{"error":"User not found"}` |
| admin API, no or bad token | 401 | `{"error":"HTTP 401 Unauthorized"}` |

The field is `error`, but the value is prose, not an OAuth error code. The two
"realm not found" messages differ between the protocol and admin endpoints, down to
the trailing period.

**Shape 3, `errorMessage`:**

| Case | Status | Body |
|---|---|---|
| duplicate client | 409 | `{"errorMessage":"Client gloak-probe already exists"}` |
| user without username | 400 | `{"errorMessage":"User name is missing"}` |

**Shape 4, RFC 6749 shape on the admin API:**

| Case | Status | Body |
|---|---|---|
| malformed JSON body | 400 | `{"error":"invalid_request","error_description":"Cannot parse the JSON"}` |

**userinfo with an invalid token** is its own case: 401, `Content-Type:
text/plain;charset=utf-8`, an **empty body**, and the error carried in a header:

```
WWW-Authenticate: Bearer realm="master", error="invalid_token", error_description="Token verification failed"
```

## Authorization code flow

The redirect back to the client carries `state`, `session_state`, `iss` and `code`.
The `iss` parameter is present because `authorization_response_iss_parameter_supported`
is true.

The authorization code is composite, three parts separated by dots:

```
8af8c832-0fcf-975e-a55a-38ea2755f967.p2oReT4cpfec5q5LnTYZhz2e.5d844f15-0f13-4b7d-aa51-4da71f020bc0
```

That is `code UUID`, `session_state`, `client session UUID`. Clients treat it as
opaque, but golden tests see the shape.

## Cookies

On `GET /auth`:

| Cookie | Attributes |
|---|---|
| `AUTH_SESSION_ID` | `Path=/realms/{realm}/`, `Secure`, `HttpOnly`, `SameSite=None`, `Version=1` |
| `KC_AUTH_SESSION_HASH` | quoted value, `Max-Age=60`, `Secure`, `SameSite=None`, no `HttpOnly` |
| `KC_RESTART` | a JWE (`dir`, `A256GCM`), `Secure`, `HttpOnly`, `SameSite=None` |

After a successful login:

| Cookie | Attributes |
|---|---|
| `KEYCLOAK_IDENTITY` | a JWT, HS512, `typ` is `Serialized-ID`, `Secure`, `HttpOnly`, `SameSite=None` |
| `KEYCLOAK_SESSION` | `Max-Age=36000`, `Secure`, `SameSite=None`, no `HttpOnly` |
| `KC_RESTART` | cleared with `Max-Age=0` |

Every cookie carries `Version=1` and `Path=/realms/{realm}/`.

## Discovery document

56 top-level keys. The endpoint paths match the design spec. Relevant defaults:

- `code_challenge_methods_supported`: `["plain", "S256"]`
- `grant_types_supported` includes `authorization_code`, `client_credentials`,
  `implicit`, `password`, `refresh_token`
- `require_request_uri_registration`: `true`
- `require_pushed_authorization_requests`: `false`
- `authorization_response_iss_parameter_supported`: `true`

## Bootstrap of the master realm

Clients created out of the box:

| clientId | public | standard flow | direct grant | service account |
|---|---|---|---|---|
| `account` | yes | yes | no | no |
| `account-console` | yes | yes | no | no |
| `admin-cli` | yes | **no** | yes | no |
| `broker` | no | yes | no | no |
| `master-realm` | no | yes | no | no |
| `security-admin-console` | yes | yes | no | no |

Realm roles: `admin` (composite), `create-realm`, `default-roles-master`
(composite), `offline_access`, `uma_authorization`.

The admin role container for the master realm is the **`master-realm` client**, which
carries 21 roles (`manage-users`, `manage-realm`, `view-clients`, `query-groups` and
so on). `realm-management` is the equivalent client inside non-master realms. The
design spec named `realm-management` for the master bootstrap, which is wrong; it is
corrected in section 8.

## Representation sizes

- `RealmRepresentation`: 106 fields
- `ClientRepresentation`: 26 fields as returned by the client list endpoint
- `UserRepresentation`: 11 fields for the bootstrapped admin

`UserRepresentation` for the admin user:

```
access, attributes, createdTimestamp, disableableCredentialTypes, emailVerified,
enabled, id, notBefore, requiredActions, totp, username
```

Note `totp` and `disableableCredentialTypes`, both legacy fields that are still
emitted, and `access`, a computed permissions block.
