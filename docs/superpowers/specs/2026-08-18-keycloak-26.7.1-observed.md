# Keycloak 26.7.1: observed behaviour

Date: 2026-08-18
Source: `quay.io/keycloak/keycloak:26.7.1`, `start-dev`, default configuration

This document records what was measured on a live instance, not what the
documentation claims. It resolves section 14 of the design spec. Values here are
the contract Gloak has to reproduce.

## Token endpoint response

Fields, in the order Keycloak emits them:

```
access_token, expires_in, refresh_expires_in, refresh_token,
token_type, id_token, not-before-policy, session_state, scope
```

`not-before-policy` is spelled with hyphens, not underscores. `id_token` is present
only when the `openid` scope was requested.

In the `master` realm `expires_in` is 60 and `refresh_expires_in` is 1800.

### `expires_in` and `refresh_expires_in` are stable across container starts

Unlike `access_token`, `refresh_token`, `id_token` and `session_state`, these two
fields are configured lifespans, not per-request or per-process randomness.
Recording `POST /realms/master/protocol/openid-connect/token` with the `admin-cli`
password grant against two independent fresh containers (2026-08-20, while fixing
the conformance harness catalogue) returned `"expires_in":60` and
`"refresh_expires_in":1800` identically both times. The only field that differed
between the two runs was `scope`'s word order (see below), which has the same
underlying cause as `scopes_supported`'s order, not this one.

Consequently `internal/conformance/catalog_oidc_pending.go`'s eight token-issuing
cases no longer list `expires_in` or `refresh_expires_in` in `Volatile`. Only one of
them - `oidc/token/password-grant-admin-cli`, the only case with a fixture today -
is actually pinned against a measured value; the other seven have no golden at all,
so they are not "pinned like any other field" yet. For those seven, removing the
mask is an inference from the one measured case, not a measurement of its own: it
assumes they share the master realm's token endpoint closely enough to see the same
values. The direction is safe - removing a path from `Volatile` writes no value
anywhere, and a wrong inference fails loudly the moment a case gains a fixture and
gets recorded - but it is an inference, not the measurement this document's rule
asks for, so it is written down as one here rather than presented as settled.

`oidc/token/refresh-token-grant` is the weakest of the seven: `refresh_expires_in`
on a *refresh* response is bounded by the remaining SSO session lifetime, not purely
by the configured refresh-token lifespan, so "configured lifespan, not randomness"
is least obviously safe there. That is a flag for whoever measures it next, not a
measurement.

## Token signing

Access and ID tokens are signed RS256. **Refresh tokens are signed HS512**, with a
different key. This is not a detail that can be skipped: a refresh token is opaque
to clients, so Keycloak signs it symmetrically.

## Claim sets

Re-measured 2026-08-23 by decoding real tokens from a confidential client. The
first cut of this section listed the claims alphabetically and said so; the
order below is the one Keycloak actually emits, and it is not alphabetical.
Nothing compares a token byte for byte - every one is `Volatile` in every
recorded response - but **introspection serves the access token's claim set as
an ordinary JSON body**, and that body is compared, so the order is contract by
proxy.

Access token, ordinary client, in order:

```
exp, iat, jti, iss, aud, sub, typ, azp, sid, acr, allowed-origins,
realm_access, resource_access, scope, email_verified, preferred_username
```

`typ` is `Bearer`. `allowed-origins` is a non-standard claim holding the
client's web origins.

**Four of those keys are absent rather than empty**, each measured both ways
round on the same client:

| Key | Absent when |
|---|---|
| `aud` | the user holds no client role |
| `allowed-origins` | the client has no `webOrigins` |
| `realm_access` | the user holds no realm role |
| `resource_access` | the user holds no client role |

A user stripped of `default-roles-master` therefore gets a token with none of
the four - not `[]`, not `{}`, not `{"roles":[]}`.

**`aud` is a string when it names one client and an array when it names
several.** `"aud":"account"` for an ordinary user, `["master-realm","account"]`
for the administrator. See "What `aud` holds" below for what goes in it.

ID token, in order:

```
exp, iat, jti, iss, aud, sub, typ, azp, sid, at_hash, acr, email_verified,
preferred_username
```

`typ` is `ID`. `aud` here is a **string always**, and it is the issuing client -
the one place the ID token and the access token name different audiences.

Refresh token, in order:

```
exp, iat, jti, iss, aud, sub, typ, azp, sid, scope, aud_x, prov
```

`typ` is `Refresh`. `aud` is the issuer URL, a string even when the access
token's `aud` is an array. `aud_x` carries what the access token puts in `aud`,
under the same absent/string/array rule. `prov` is `default`.

**The refresh token's `scope` is not a fixed list.** It is the granted scope
followed by the client's default client scopes that are not already in it:

| Client | Granted | Refresh `scope` |
|---|---|---|
| `admin-cli` | `profile email` | `profile email web-origins acr basic roles` |
| `admin-cli`, `scope=openid` | `openid profile email` | `openid profile email web-origins acr basic roles` |
| service-account client | `openid profile email` | the above plus `service_account` |

The first cut of this section recorded it as a constant
`openid email acr roles basic service_account web-origins profile`, which is
wrong in both directions: `openid` appears only when it was asked for, and
`service_account` only on a client with service accounts enabled - it is that
client's seventh default client scope.

`jti` on access tokens carries an instance prefix, for example
`onrtro:13f91f50-6b34-71c7-6d86-d201ef27be67`. ID and refresh tokens use a plain
UUID. This is a normalisation target for golden tests.

### What `aud` holds

`aud` is the clients the **user** holds roles on - the keys of
`resource_access` - **minus the issuing client**.

The exclusion was measured directly: assigning the administrator a role on the
very client requesting the token puts that client in `resource_access` and
leaves it out of `aud`. So a client can never introspect a token it asked for
itself, and that is the contract rather than an accident of it. A *second*
confidential client, named in the aud because the user holds a role on it, does
introspect the same token successfully.

`aud` is in the same order as `resource_access`'s keys, which is Keycloak's
Java map order - see below.

### Java map key order

Keycloak serialises Java `Map`s and `Set`s in `HashMap` iteration order, which
looks arbitrary and is exactly determined: the table is walked from bucket 0
upwards, and a key's bucket is

```
(h ^ (h >>> 16)) & (capacity - 1)      // h = String.hashCode, capacity 16 until 12 entries
```

Measured 2026-08-23 and confirmed on four independent key sets, reproduced in
`internal/javamap`:

| Key set | Order |
|---|---|
| the `access` block of a user read | `manageGroupMembership, resetPassword, view, mapRoles, impersonate, manage` |
| `resource_access` clients | `master-realm, account` |
| `realm_access.roles` | `create-realm, default-roles-master, offline_access, admin, uma_authorization` |
| `account` roles | `manage-account, manage-account-links, view-profile` |

**The one thing this does not settle is a bucket collision.** Two keys in the
same bucket are chained in insertion order, which nothing observable reveals.
The 21 admin role names collide in two buckets - `view-realm` with
`view-identity-providers`, `query-organizations` with `query-groups` - and both
pairs come back the other way round from a sorted tie-break. Every one of the
other seventeen positions is right, which is what says the rule holds and only
the tie-break does not. A conformance case comparing a large key set has to say
so with `Case.Unordered`.

This supersedes nothing that was written down, because nobody had looked: the
`access` block's order was transcribed as "a Java Map's hash order,
deterministic for this key set" without the rule behind it.

## Lightweight access tokens

The `admin-cli` client ships with
`client.use.lightweight.access.token.enabled = true`. Its access tokens therefore
carry only:

```
azp, exp, iat, iss, jti, scope, sid, typ
```

No `sub`, no `aud`, no `realm_access`. Any bootstrap that creates `admin-cli`
without this attribute will produce tokens that do not match the original.

## Password hashing

The default for a bootstrapped admin user:

```json
{
  "hashIterations": 5,
  "algorithm": "argon2",
  "additionalParameters": {
    "hashLength": ["32"],
    "memory": ["7168"],
    "type": ["id"],
    "version": ["1.3"],
    "parallelism": ["1"]
  }
}
```

Argon2id, version 1.3, 5 iterations, 7168 KiB of memory, parallelism 1, 32-byte
output. Note that the parameter values are arrays of strings.

## Error formats

There are **four** distinct shapes, not two. This is the single most important
finding in this document.

**Shape 1, RFC 6749 on the token endpoint:**

| Case | Status | Body |
|---|---|---|
| wrong password | 400 | `{"error":"invalid_grant","error_description":"Invalid user credentials"}` |
| unknown client | 401 | `{"error":"invalid_client","error_description":"Invalid client or Invalid client credentials"}` |
| wrong client secret | 401 | `{"error":"unauthorized_client","error_description":"Invalid client or Invalid client credentials"}` |
| missing `grant_type` | 400 | `{"error":"invalid_request","error_description":"Missing form parameter: grant_type"}` |
| unknown `grant_type` | 400 | `{"error":"unsupported_grant_type","error_description":"Unsupported grant_type"}` |
| bad or replayed code | 400 | `{"error":"invalid_grant","error_description":"Code not valid"}` |
| bad refresh token | 400 | `{"error":"invalid_grant","error_description":"Invalid refresh token"}` |

An unknown client and a wrong secret return **different error codes** with identical
descriptions. A replayed authorization code is indistinguishable from a fabricated
one.

**Shape 2, bare `error` with a human message:**

| Case | Status | Body |
|---|---|---|
| discovery for unknown realm | 404 | `{"error":"Realm does not exist"}` |
| admin API, unknown realm | 404 | `{"error":"Realm not found."}` |
| admin API, unknown user | 404 | `{"error":"User not found"}` |
| admin API, no or bad token | 401 | `{"error":"HTTP 401 Unauthorized"}` |

The field is `error`, but the value is prose, not an OAuth error code. The two
"realm not found" messages differ between the protocol and admin endpoints, down to
the trailing period.

**Shape 3, `errorMessage`:**

| Case | Status | Body |
|---|---|---|
| duplicate client | 409 | `{"errorMessage":"Client gloak-probe already exists"}` |
| user without username | 400 | `{"errorMessage":"User name is missing"}` |

**Shape 4, RFC 6749 shape on the admin API:**

| Case | Status | Body |
|---|---|---|
| malformed JSON body, on an endpoint taking one object | 400 | `{"error":"invalid_request","error_description":"Cannot parse the JSON"}` |
| malformed JSON body, on an endpoint taking an **array** | 400 | `{"error":"unknown_error","error_description":"Cannot parse the JSON"}` |

**The `error` code is not the same on every endpoint**, which this row read as
unqualified until 2026-08-26. The description is identical and the code is not:
the ten registrations that take a JSON **array** - the six composite writes and
the four role-mapping writes - answer `unknown_error`, and everything measured
that takes a single object answers `invalid_request`. Both forms of bad body
give an endpoint its own one answer, so this is not a parse-versus-shape
distinction. The full sweep is under "The array endpoints say `unknown_error`,
where `POST /users` says `invalid_request`". The count read eight until
2026-08-26: the two client-mapping writes were left out because they were not
shipped, and they were measured on the day they landed rather than assumed from
the other eight.

**userinfo with an invalid token** is its own case: 401, `Content-Type:
text/plain;charset=utf-8`, an **empty body**, and the error carried in a header:

```
WWW-Authenticate: Bearer realm="master", error="invalid_token", error_description="Token verification failed"
```

## Authorization code flow

The redirect back to the client carries `state`, `session_state`, `iss` and `code`.
The `iss` parameter is present because `authorization_response_iss_parameter_supported`
is true.

The authorization code is composite, three parts separated by dots:

```
8af8c832-0fcf-975e-a55a-38ea2755f967.p2oReT4cpfec5q5LnTYZhz2e.5d844f15-0f13-4b7d-aa51-4da71f020bc0
```

That is `code UUID`, `session_state`, `client session UUID`. Clients treat it as
opaque, but golden tests see the shape.

## Discovery document

56 top-level keys. The endpoint paths match the design spec. Relevant defaults:

- `code_challenge_methods_supported`: `["plain", "S256"]`
- `grant_types_supported` includes `authorization_code`, `client_credentials`,
  `implicit`, `password`, `refresh_token`
- `require_request_uri_registration`: `true`
- `require_pushed_authorization_requests`: `false`
- `authorization_response_iss_parameter_supported`: `true`

### `scopes_supported` order is not stable across restarts

`scopes_supported` in the discovery document carries these thirteen values:

```
openid, roles, acr, service_account, email, organization, offline_access,
microprofile-jwt, phone, web-origins, basic, profile, address
```

Observed over three container starts of `quay.io/keycloak/keycloak:26.7.1`
while building the conformance recorder's idempotence check (2026-08-20),
independently reproduced over three further starts: the order of the twelve
values after `openid` differs on every fresh start, while repeated requests
against one already-running container always return the order that instance
started with. That points to a Java set's iteration order, fixed once at
startup rather than randomized per request. `openid` came first in all six
starts across both rounds; the other twelve were shuffled differently each
time.

Six starts is not enough runs to state a guarantee about `openid` always
sorting first - it is what was observed, not a proven invariant. Given this,
the conformance harness does not pin `scopes_supported`'s order at all: the
`oidc/discovery/master` case lists it in `Unordered` (see
`internal/conformance/case.go`), which asserts the thirteen values and their
count while dropping the order assertion entirely.

### Token response `scope` word order is also not stable across container starts

Same family as the `scopes_supported` finding directly above - a Java set
serialised with no fixed order - just surfacing somewhere else. The token
endpoint's response includes a space-separated `scope` string (see "Token
endpoint response" above), and the order of its words is not stable either.
Recording `POST /realms/master/protocol/openid-connect/token` with the
`admin-cli` password grant (`grant_type=password`, no explicit `scope` form
field) across four independent container starts while building the
conformance harness's pending-case inventory (2026-08-20) produced
`"scope":"profile email"` on three starts and `"scope":"email profile"` on
one. Four starts is not enough to say anything about which order is more
common, only that both were observed and repeated requests within one
already-running container returned that instance's own order consistently -
the same "fixed at startup, not randomised per request" pattern already
established for `scopes_supported` and the `certs` `keys` array.

Consequently `internal/conformance/catalog_oidc_pending.go`'s
`oidc/token/password-grant-admin-cli` case (currently `Pending`, so nothing
compares it yet) carries a comment noting the churn rather than an attempt to
mask it: neither `Volatile` (whole-value replacement) nor `Unordered`
(JSON-array element reordering) can address word order inside a single
string value, so this will need a new mechanism, or a value comparison that
splits and sorts the scope string, before that case can go green.

## Certificate endpoint

`GET /realms/{realm}/protocol/openid-connect/certs`. Recorded while building the
conformance harness (2026-08-20), captured in
`internal/conformance/testdata/golden/oidc/certs/master.http` and confirmed by
querying a second, freshly started container directly for the un-normalised
values (the golden marks `x5c`, the thumbprints, `kid` and `n` volatile, since
they are regenerated per process).

**The `master` realm publishes two keys, not one:**

```json
{"keys":[
  {"kid":"...","kty":"RSA","alg":"RS256","use":"sig","x5c":["..."],"x5t":"...","x5t#S256":"...","n":"...","e":"AQAB"},
  {"kid":"...","kty":"RSA","alg":"RSA-OAEP","use":"enc","x5c":["..."],"x5t":"...","x5t#S256":"...","n":"...","e":"AQAB"}
]}
```

One `RS256`/`sig` key (used for RS256 token signing) and one `RSA-OAEP`/`enc`
key (a separate encryption key Gloak does not generate; tracked as part of F5
in the follow-ups document).

### `keys` array order is not stable across container starts

Six independent container starts were compared while making `make record`
idempotent for this case (2026-08-20): three through the conformance
recorder's testcontainers path, three through a plain `docker run` against
the same image and environment. Within each group the order was internally
consistent - all three testcontainers starts put `RS256`/`sig` first, all
three plain `docker run` starts put `RSA-OAEP`/`enc` first - but the two
groups disagree with each other, and nothing about the harness or the request
differs between them beyond how the container was launched. Six runs is not
enough to characterise *why* it splits along that line (guessing would break
the project's own rule), but it is enough to say plainly that the order is
not guaranteed: it must be treated as unstable, the same standard applied to
`scopes_supported` above, rather than assumed stable because a few
consecutive runs agreed.

Consequently the `oidc/certs/master` case marks `Unordered: []string{"keys"}`
(`internal/conformance/catalog_oidc.go`). Sorting the array only produces a
stable, idempotent recording because the harness's Normalize pass now runs
*before* SortUnordered (`internal/conformance/record_test.go`,
`internal/conformance/conformance_test.go`): with `kid` - the first field in
each entry, and volatile - masked to a placeholder first, the sort falls
through to the first field that still differs, `alg` (`"RS256"` sorts before
`"RSA-OAEP"`). Sorting on the raw, un-normalised bytes first (the harness's
original pass order) was tried and measured to be non-idempotent: two
consecutive `make record` runs happened to agree, a third flipped the order,
because the sort was actually keying off the random `kid` value rather than
`alg`/`use`.

**Field order within one key entry**, transcribed byte-by-byte from the
golden and not from go-jose's own marshalling (which orders
`use, kty, kid, alg, n, e, x5c, x5t, x5t#S256`):

```
kid, kty, alg, use, x5c, x5t, x5t#S256, n, e
```

**Base64 variants are not uniform across the entry.** Confirmed against an
un-normalised capture:

- `x5c`: standard base64 **with** padding (RFC 7517's `+`/`/` alphabet, `=`
  padding present) - it is a certificate, not a JWK-spec integer.
- `x5t`, `x5t#S256`, `n`, `e`: base64url **without** padding (`-`/`_`
  alphabet, no `=`), per the JWK spec (RFC 7517/7518).

**The certificate.** `x5c` decodes (via `openssl x509 -inform DER`) to a
self-signed certificate: `Subject: CN=master`, `Issuer: CN=master` (same,
self-signed), 2048-bit RSA key, `sha256WithRSAEncryption`. Validity observed
on one capture: `Not Before: Aug 20 18:44:24 2026 GMT`,
`Not After: Aug 20 18:46:04 2036 GMT` - a roughly-10-year window starting near
container startup, not from the Unix epoch. Both the `sig` and `enc` keys'
certificates share the identical `CN=<realm-name>` subject pattern.

## Realm info endpoint

`GET /realms/{realm}`, the public realm descriptor adapters use. Recorded while
building the conformance harness (2026-08-20), captured in
`internal/conformance/testdata/golden/realm/info/master.http` and
`.../realm/info/unknown-realm.http`.

**Field order**, transcribed from the golden:

```
realm, public_key, token-service, account-service, tokens-not-before
```

This matches the order `internal/oidc/router.go`'s `realmInfoDocument` already
used - it was written from memory against a live instance and happened to be
right, but it was a guess until this recording, per F3 in the follow-ups
document. `public_key` is marked `Volatile` in the conformance case: the realm
signing key is generated per process, so its PKIX DER encoding differs on
every run.

**The success response's `Content-Type` carries a charset**:
`application/json;charset=UTF-8`, unlike every other endpoint measured so far
(discovery, certs), which send plain `application/json`. The 404 for an
unknown realm does not: it sends plain `application/json`, matching
`WriteMessageError`'s shape used across the rest of the protocol surface.
`internal/httpx.WriteJSONCharset` exists for this one case.

The unknown-realm case returns the same shape 2 body (`{"error":"Realm does
not exist"}`) and 404 status already measured for other protocol endpoints;
nothing new there.

## Fallback responses

Two cases outside Keycloak's documented endpoint set: a path matching no
route at all, and a path that matches a route but not the method it
requires. Recorded while building the conformance harness (2026-08-20),
captured in
`internal/conformance/testdata/golden/http/fallback/unknown-path.http` and
`.../http/fallback/method-not-allowed.http`.

**A path matching no route**, `GET /nosuchpath`, sends 404 with a message
distinct from the generic shape used elsewhere:

```json
{"error":"Unable to find matching target resource method"}
```

No `Referrer-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options`,
`X-Frame-Options` or `X-Robots-Tag` header is present - this request never
reaches the filter chain that adds them. It is not the only response missing
one of the five, though: see "Userinfo omits X-Frame-Options" below.

**A known path with the wrong method**, `POST
/realms/master/.well-known/openid-configuration` (only `GET` is valid),
also sends **404, not 405**:

```json
{"error":"HTTP 404 Not Found"}
```

That is shape 2's generic "HTTP `<code>` `<reason>`" message, with the code
fixed at 404 regardless of which method was actually rejected. There is no
`Allow` header naming the methods that would have been accepted. Unlike the
unmatched-path case above, the five security headers are present, since this
request does reach the filter chain a known resource sits behind.

Both cases send plain `Content-Type: application/json`, matching
`internal/httpx.WriteMessageError`'s shape.

## Userinfo rejections

Measured 2026-08-21 while recording P1's contract. Four distinct refusals, all
`text/plain;charset=utf-8` with an empty body and the error carried in
`WWW-Authenticate`:

| Case | Status | `WWW-Authenticate` |
|---|---|---|
| no `Authorization` header | 401 | `Bearer realm="master"` - no `error` at all |
| garbage bearer token | 401 | `error="invalid_token"`, `error_description="Token verification failed"` |
| token without the `openid` scope | 403 | `error="insufficient_scope"`, `error_description="Missing openid scope"` |
| lightweight access token | 401 | `error="invalid_token"`, `error_description="Lightweight access token not allowed for userinfo endpoint"` |

The first row is why `internal/httpx.WriteBearerChallenge` takes an empty error
code as meaning "emit the bare challenge" rather than always writing the
`error`/`error_description` pair, and why it takes a status: the third row is a
403 and the rest are 401s.

The last one has a consequence worth stating plainly, because it blocks work
rather than merely describing a response: **no client a fresh `master` realm
bootstraps can obtain a token userinfo will accept.** `admin-cli` is the only
one of the six with direct access grants enabled, and it carries
`client.use.lightweight.access.token.enabled = true`, which userinfo refuses
whatever scope was requested. Reaching the success body needs a completed
browser login or a client created through the admin API.

The scope refusal is separate from the lightweight one and comes first only
in the sense that it is what a scopeless request hits: requesting
`scope=openid` from `admin-cli` moves the response from the 403 to the 401,
it does not reach a 200.

### Userinfo's rejections omit X-Frame-Options

A userinfo **rejection** sends four of the five security headers -
`Referrer-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options` and
`X-Robots-Tag` - and **not** `X-Frame-Options`. Measured on all five recorded
rejections, across 401 and 403, in four separate recording runs.

This makes userinfo the second exception to "the five reach every response",
after the unmatched-path 404 above, and unlike that one it is a route that
does reach the filter chain. AGENTS.md stated the single-exception version
before this was measured.

**Corrected 2026-08-23: it is the rejections, not the endpoint.** The success
body, which nothing could reach until a confidential client became creatable,
carries all five. The heading and the first sentence here said "userinfo" flat
until the 200 was recorded - see "The bodies P1 could not reach" below.

The catalogue pins it with `AssertAbsentHeaders`, since `AssertHeaders` can
only ever check a header that is named and would never catch an
implementation that started sending it everywhere for consistency.

## Revocation accepts a public client; introspection does not

Both measured against `admin-cli`, which is public.

`POST .../revoke` returns **200 with an empty body** - no `Content-Type`, no
`Cache-Control` - for a valid access token and a valid refresh token. A wrong
client gives 401.

Corrected 2026-08-22, while implementing P1: an earlier version of this
paragraph said an unknown token was answered the same empty 200. The recorded
bytes say otherwise. `internal/conformance/testdata/golden/oidc/revocation/unknown-token.http`
is a **200 carrying an error body**,
`{"error":"invalid_token","error_description":"Invalid token"}`, with
`Content-Type: application/json`. The status is shared with the success and
the body is not. The goldens are the recording; this document was summarising
them and got it wrong.

The two successes carry a header nothing else recorded does:

```
Content-Security-Policy: frame-src 'self'; frame-ancestors 'self'; object-src 'none';
```

Neither the unknown-token 200 nor the wrong-client 401 carries it, so it is not
a revocation-endpoint header but a revocation-*success* header. The two
successful cases pin it with `AssertHeaders` and pin the absent `Content-Type`
with `AssertAbsentHeaders`; before P1 they asserted `Content-Type` instead,
which no golden had, and would have failed on promotion for a reason that said
nothing about the implementation.

`POST .../token/introspect` refuses outright with **403**

## Admin API rejection shapes

Measured 2026-08-22. All of them are shape 2 - a bare `error` field holding
prose - with `Content-Type: application/json` and all five security headers.
**None carries a `WWW-Authenticate` header**, so the admin API's rejections are
a different family from `userinfo`'s, which carries its error entirely in that
header.

| Case | Status | Body |
|---|---|---|
| no `Authorization` header | 401 | `{"error":"HTTP 401 Unauthorized"}` |
| garbage bearer token | 401 | `{"error":"HTTP 401 Unauthorized"}` |
| caller lacking the required role | 403 | `{"error":"HTTP 403 Forbidden"}` |
| user that does not exist | 404 | `{"error":"User not found"}` |
| client that does not exist | 404 | `{"error":"Could not find client"}` |
| realm that does not exist | 404 | `{"error":"Realm not found."}` |

Two things worth stating plainly.

**A missing header and a garbage token are indistinguishable.** Both give the
identical body and status, unlike the protocol side, where `userinfo`
distinguishes them. Reporting them differently would be a divergence.

**The three 404 messages are three different strings.** `User not found`,
`Could not find client` and `Realm not found.` - and only the last has a
trailing period. A shared "not found" helper would get two of the three wrong.

### The admin 401 and 403 reuse the generic HTTP-status body

`{"error":"HTTP 401 Unauthorized"}` is the same construction as the protocol
side's `{"error":"HTTP 404 Not Found"}`, already recorded under "Fallback
responses" for a known path hit with the wrong method: the word `HTTP`, the
status code, then its reason phrase. It is not an admin-specific format.

```
HTTP/1.1 201 Created
Location: http://localhost:18091/admin/realms/master/clients/d837b355-162c-4c54-b2f7-e709041b34e3
Referrer-Policy: no-referrer
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

**No `Content-Type`, no body**, and the new object's identity is carried only by

verifier's in-process handler, so a case has to capture the final path segment
rather than the whole URL.

### Writing a client: four statuses, four different header sets

Measured 2026-08-22 on the `clients` endpoints. Every row is a different shape,
and none of them can be inferred from its neighbour:

| Operation | Status | Body | Notable headers |
|---|---|---|---|
| create | 201 | empty | `Location` absolute; **no `Content-Type`** |
| create, duplicate clientId | 409 | `{"errorMessage":"Client <id> already exists"}` | `application/json` |
| update | 204 | empty | no `Cache-Control`, no `Content-Length` |
| delete | 204 | empty | `Cache-Control: no-cache`, and **no `X-Frame-Options`** |
| delete, unknown UUID | 404 | `{"error":"Could not find client"}` | `application/json` |

Two of those deserve stating on their own.

**The delete 204 omits `X-Frame-Options`.** That makes it the **third**
exception to "the five security headers reach every response", after the
unmatched-path 404 and `userinfo`. Update's 204 sits next to it with all five
present and no `Cache-Control`, so it is not a rule about 204s or about the
admin API.

It is a rule about `DELETE` - see "The X-Frame-Options omission follows the
method" below, measured 2026-08-23 across four `DELETE`s and two `PUT`s. When
this section was written only one `DELETE` had been measured, so it read as a
one-off.

**A duplicate clientId answers shape 3, not shape 1.** The token endpoint's
conflicts are RFC 6749 bodies; this one is `errorMessage`. The observed
"Error formats" section already listed `{"errorMessage":"Client gloak-probe
already exists"}` and this recording confirms the pattern with the clientId
interpolated.

### Client attribute key order

`attributes` is a Java `Map` serialised in hash order: deterministic for a
given key set, but a function of Java's string hashing rather than of anything
Keycloak decided. Go sorts map keys alphabetically.

**This is the one place the conformance suite gives up on byte-exactness**, and
it is deliberate. Reproducing the order would mean emulating
`java.util.HashMap`'s iteration order in Go - a large amount of fragile code to
match an order no client can depend on and no documentation states.
`Case.UnorderedKeys` sorts both sides, so membership and values stay asserted.

### The X-Frame-Options omission follows the request's Content-Type

**Corrected 2026-08-23.** This section first read "follows the method", from
six 204s in which every `DELETE` sent no `Content-Type` and every `PUT` sent
JSON. `PUT .../credentials/{id}/userLabel`, which sends `text/plain` and omits
the header, falsified that.

`DELETE /users/{id}` was then sent seven times with seven different
`Content-Type` headers. Every one answered 204:

| Request `Content-Type` | `X-Frame-Options` |
|---|---|
| absent | absent |
| `text/plain` | absent |
| `*/*` | absent |
| `application/json` | **present** |
| `application/json;charset=UTF-8` | **present** |
| `application/xml` | **present** |
| `application/x-www-form-urlencoded` | **present** |

So a 204 carries the header exactly when the request declared an
`application/*` body. It holds across every 204 measured elsewhere:

| Request | `Content-Type` | `Cache-Control` | `X-Frame-Options` |
|---|---|---|---|
| `PUT /clients/{uuid}` | json | absent | present |
| `PUT /users/{id}` | json | absent | present |
| `PUT .../reset-password` | json | absent | present |
| `PUT .../disable-credential-types` | json | absent | present |
| `PUT .../credentials/{id}/userLabel` | `text/plain` | absent | **absent** |
| `POST .../credentials/{id}/moveToFirst` | none | absent | absent |
| `POST .../credentials/{id}/moveAfter/{id}` | none | absent | absent |
| `DELETE /clients/{uuid}` | none | `no-cache` | absent |
| `DELETE /users/{id}` | none | `no-cache` | absent |
| `DELETE /roles/{name}` | none | `no-cache` | absent |
| `DELETE .../credentials/{id}` | none | `no-cache` | absent |
| `DELETE .../client-secret/rotated` | none | absent | absent |

It applies to the 204 only: the same `DELETE /clients/{uuid}` answering 404 for
an unknown UUID sends all five, as does `DELETE .../client-secret/rotated`
answering 500 to a caller without the role. A 200 sends all five whatever the
request declared.

`Cache-Control` is independent and has to be pinned per endpoint: four of the
five measured deletes carry `no-cache` and `DELETE .../client-secret/rotated`
does not, while no `PUT` carries one.

## Client secrets

Measured 2026-08-23. Five operations, and the interesting ones are the
absences.

| Request | Status | Body | Notable headers |
|---|---|---|---|
| `GET .../client-secret` | 200 | `{"type":"secret","value":"<86 chars>"}` | `Cache-Control: no-cache`, charset |
| `GET .../client-secret`, no secret stored | 200 | `{"type":"secret"}` | `Cache-Control: no-cache`, charset |
| `POST .../client-secret` | 200 | `{"type":"secret","value":"<86 chars>"}` | **no `Cache-Control`**, charset |
| `GET .../client-secret/rotated` | 404 | `{"error":"Client does not have a rotated secret"}` | `application/json` |
| `DELETE .../client-secret/rotated` | 204 | empty | no `Cache-Control`, no `X-Frame-Options` |
| any of them, unknown UUID | 404 | `{"error":"Could not find client"}` | `application/json` |

**`GET` carries `Cache-Control: no-cache` and `POST` does not**, on two
responses with the same body shape and the same `Content-Type`. Reading and
regenerating a secret are the same handler in shape and differ here.

**A client with no secret answers 200, not 404**, and the `value` key is simply
absent. **None of the six bootstrapped clients in `master` has a secret** -
`account`, `account-console`, `admin-cli`, `security-admin-console`, `broker`
and `master-realm` all answer `{"type":"secret"}`. That is why `secret` never
appeared in the recorded client representations.

**`POST` mints a secret for a public client too.** It is not refused, and
afterwards `GET` returns the value. The representation still omits it, so the
two endpoints disagree about the same client on purpose.

### `secret` in the representation follows `publicClient`, not storage

A stored secret appears in `ClientRepresentation` only when the client is not
public:

| Client | `publicClient` | `bearerOnly` | secret stored | `secret` in representation |
|---|---|---|---|---|
| created confidential | false | false | yes | **yes** |
| created bearer-only | false | true | yes | **yes** |
| created public | true | false | yes, after a `POST` | **no** |
| bootstrapped `broker` | false | true | no | no |

`bearerOnly` does not suppress it. A public client that has been given a secret
by `POST .../client-secret` still shows none, which is the row that rules out
"the representation shows whatever is stored".

Every client created through the API gains two attributes, public or not:
`realm_client` set to `"false"` and `client.secret.creation.time` holding a unix
second. The bootstrapped clients carry `realm_client` and no creation time.

### Which role each client operation needs

Measured 2026-08-23 by creating three users in the reference container, giving
each exactly one `master-realm` client role through the role-mapping API, and
calling every operation with a token obtained for that user. This is the first
time these were measured rather than inferred from the role names.

| Operation | `view-clients` | `manage-clients` | `query-clients` |
|---|---|---|---|
| `GET /clients` | 200 | 200 | **200, and the array is empty** |
| `GET /clients/{uuid}` | 200 | 200 | 403 |
| `POST /clients` | 403 | 201 | 403 |
| `PUT /clients/{uuid}` | 403 | 204 | 403 |
| `DELETE /clients/{uuid}` | 403 | 204 | 403 |
| `GET .../client-secret` | 200 | 200 | 403 |
| `POST .../client-secret` | 403 | 200 | 403 |
| `GET .../client-secret/rotated` | 404 | 404 | 403 |
| `DELETE .../client-secret/rotated` | **500** | 204 | **500** |
| `GET .../service-account-user` | 200 | 200 | 403 |

**Reading a secret needs only `view-clients`.** Regenerating one needs
`manage-clients`. The two sit on the same path and differ.

**`GET /clients` is not gated, it is filtered.** A `query-clients` caller gets
200 and an empty array, even filtering to a client that exists. The listing
returns the objects the caller may view rather than refusing the caller.

**`DELETE .../client-secret/rotated` answers 500 to a caller who lacks
`manage-clients`,** not 403, and the server log shows why:

```
Uncaught server error: java.lang.NullPointerException: Cannot invoke
"java.lang.Throwable.getMessage()" because the return value of
"java.lang.RuntimeException.getCause()" is null
```

The body is `{"error":"unknown_error","error_description":"For more on this
error consult the server log."}` with plain `application/json`, and unlike the
204 on the same path it **does** carry `X-Frame-Options`. Reproduced three
times across two callers. The 404 path on the same route is unaffected: an
unknown UUID still answers `{"error":"Could not find client"}`.

This is a Keycloak defect and it is also the contract. Gloak reproduces it.

### A rotated secret cannot exist on a default 26.7.1

`GET .../client-secret/rotated` answers 404 unconditionally, and `DELETE`
answers 204 unconditionally, because there is nothing to rotate:

- `CLIENT_SECRET_ROTATION` is reported by `/admin/serverinfo` as
  `{"type":"PREVIEW","enabled":false}`.
- `secret-rotation` is **not** among the 35 registered `client-policy-executor`
  providers, so a client profile naming it is rejected with
  `{"errorMessage":"proposed client profile contains the executor, which does
  not have valid provider, or has invalid configuration."}`.

The routes are registered regardless of the feature flag, which is why they
answer at all. The 200 shape of a rotated secret is therefore **unmeasured and
unmeasurable** on the distribution this project copies, and Gloak's constant 404
is the whole contract rather than a stub.

`DELETE .../client-secret/rotated` is idempotent: a second call answers 204 the
same way.

### An expired access token

```
401, Content-Type: text/plain;charset=utf-8, empty body
WWW-Authenticate: Bearer realm="master", error="invalid_token", error_description="Token verification failed"
```

Byte-identical to the rejection of a garbage token, so userinfo does not
distinguish "this was never a token" from "this token has expired".

Reaching it needed the client attribute **`access.token.lifespan`**. Set to
`"1"` it makes `expires_in` 1 and the token is refused a second later. Two
neighbouring values were measured and neither produces a token born expired:
`"0"` yields `expires_in` 0 with a token the server still accepts, and `"-1"`
falls back to **36000** rather than to this realm's 60. So the only route to an
expired token is to wait for one, which is why `Fixture.Delay` exists.

### Introspection refuses to call an access token active outside its audience

A freshly minted, unexpired access token introspects as `{"active":false}`,
with 200 and no hint in the body. The server log says why:

```
type="INTROSPECT_TOKEN_ERROR" … error="invalid_token"
reason="Client 'gloak-confidential' is not in the token audience"
```

An access token's `aud` holds the clients the **user** has roles on -
`["master-realm","account"]` for the administrator - and never the issuing
client. So a client cannot introspect a token it asked for itself.

`aud` is a **string when there is one audience and an array when there are
several**: the service account's token carries `"aud":"account"`, the
administrator's carries `["master-realm","account"]`.

The check applies to access tokens only. A refresh token introspects active
from the same client.

Two further measurements, 2026-08-23:

- **A token with no `aud` at all is inactive too.** A user stripped of
  `default-roles-master` gets a token with no audience claim, and it is refused
  the same way.
- **A second confidential client, named in the `aud`, does introspect it
  successfully.** The user was given a role on `gloak-confidential`, and a
  token issued by `gloak-confidential-2` came back active from
  `gloak-confidential`. So the check really is membership of the audience, not
  a blanket refusal of access tokens. `client_id` in that body is the token's
  `azp`, not the caller's.

### A refresh token introspects into the access token's claim set

Not RFC 7662's small set. Keycloak rebuilds the *access* token's claims from
the token presented and appends four keys:

```
exp, iat, jti, iss, aud, sub, typ, azp, sid, acr, realm_access,
resource_access, scope, email_verified, preferred_username,
client_id, username, token_type, active
```

`typ` and `token_type` both carry the presented token's own type, so a refresh
token introspects as `Refresh` in both places. `active` comes last, and `aud`
merges the token's own audiences with the ones resolved now - so a refresh
token, whose `aud` is the realm URL, comes back naming the realm *and* the
user's clients. There is no `allowed-origins`.

The same absent/string/array rules apply here as on the token: a user holding
no client role introspects with `aud` still the bare realm URL as a string, and
with no `realm_access` and no `resource_access` at all.

**The roles are resolved at introspection time, not read out of the token.**
That is what lets a refresh token - which carries none - come back with the
full set, and it was measured: a role assigned after the token was minted
appears in the body.

An **ID token** introspects the same way, `typ` and `token_type` both `ID`, and
with **no `scope` key** since an ID token has none. Gloak does not serve this:
its introspection parses an access token or a refresh token and nothing else.
See follow-up F21.

## User representation

Measured 2026-08-23 on a user carrying every field, created through the admin
API.

```
id, username, firstName, lastName, email, emailVerified, attributes, enabled,
createdTimestamp, totp, disableableCredentialTypes, requiredActions,
notBefore, access
```

**`attributes` sits between `emailVerified` and `enabled`**, which is not where
anybody would put it. The bootstrapped administrator is the only user in a
fresh master realm that has any, and it has exactly one:

```json
"attributes":{"is_temporary_admin":["true"]}
```

Without it the user listing cannot be reproduced, so `internal/bootstrap` sets
it. What it goes on to mean is not measured.

### One user, three serialisations

The same user comes back differently from three endpoints, and the difference
is entirely in `access`:

| Request | `access` |
|---|---|
| `GET /users` | `{"manage":…}` - one key |
| `GET /users/{id}` | six keys |
| `GET .../clients/{uuid}/service-account-user` | **absent** |

A shared user serialiser would be wrong twice.

### `access` is the caller's permissions, per flag

Measured by giving a user exactly one `master-realm` role and reading the
administrator through it. The block describes what the **caller** may do, never
anything about the user being read:

| Flag | Role |
|---|---|
| `manageGroupMembership` | `manage-users` |
| `resetPassword` | `manage-users` |
| `view` | `view-users` or `manage-users` |
| `mapRoles` | `manage-users` |
| `impersonate` | `impersonation` |
| `manage` | `manage-users` |

Key order is a Java `Map`'s hash order, deterministic for this key set, and it
is not alphabetical: `manageGroupMembership, resetPassword, view, mapRoles,
impersonate, manage`.

### briefRepresentation drops four fields

`?briefRepresentation=true` removes `totp`, `disableableCredentialTypes`,
`requiredActions` and `notBefore`, and keeps `access`. Their natural values are
`false`, `[]`, `[]` and `0`, so nothing but a recording distinguishes "dropped"
from "empty" - which is why Gloak holds all four as pointers.

### Filters: two families that do not agree

`search` matches `username`, `firstName`, `lastName` or `email`; the four named
parameters each match their own field. **They are not the same comparison**,
and this section said they were until 2026-08-23 - the four measurements it was
written from all happened to be prefixes.

The named filters are case-insensitive **substrings**, and `*` is a literal:

| Query | Matches `full-user` |
|---|---|
| `username=full` | yes |
| `username=ull` | **yes** - a substring, not a prefix |
| `username=FULL-USER` | yes |
| `username=*user` | **no** - `*` is not a wildcard here |
| `username=full&exact=true` | no |
| `username=FULL-USER&exact=true` | yes |

`search` is a case-insensitive **prefix**, with `*` as a wildcard and quotes
for equality:

| Query | Matches `full-user` |
|---|---|
| `search=full` | yes |
| `search=user` | **no** - the term is a prefix |
| `search=ovelace` (of `Lovelace`) | no |
| `search=user*` | no - an explicit `*` is the whole pattern |
| `search=*user` | yes |
| `search=*ull*` | yes |
| `search="full-user"` | yes |
| `search="full"` | no |
| `search=full&exact=true` | yes - `exact` does not reach `search` |

Whether a term containing spaces splits into several is not measured.

A filter matching nothing answers 200 and `[]`, never 404.

### The listing is sorted, and count is not filtered by visibility

Users created in the order `full-user`, `zzz-user`, `aaa-user` come back as
`aaa-user, admin, full-user, zzz-user`. The listing sorts by username.

`GET /users/count` returns a **bare JSON number**, not an object, with the
charset `Content-Type` and `Cache-Control: no-cache` the listing carries.

A caller holding only `query-users` was measured getting `[]` from the listing
and **7** from the count, on the same realm at the same moment. The listing is
filtered by what the caller may view; the count is not.

### Which role each user operation needs

| Operation | `view-users` | `query-users` | `manage-users` |
|---|---|---|---|
| `GET /users` | 200 | 200, and the array is empty | 200 |
| `GET /users/count` | 200 | 200 | 200 |
| `GET /users/{id}` | 200 | **403** | 200 |

An unknown ID answers 404 `{"error":"User not found"}` - a third spelling,
against the client endpoints' "Could not find client" and the realm's "Realm
not found." with its full stop.

`POST`, `PUT` and `DELETE` all need `manage-users`; `view-users` and
`query-users` are answered 403.

### Writing a user: one endpoint, four error families

Measured 2026-08-23. `POST /users` alone answers in four different shapes:

| Body | Status | Response |
|---|---|---|
| valid | 201 | empty, absolute `Location`, **`content-length: 0`** and no `Content-Type` |
| duplicate username | 409 | `{"errorMessage":"User exists with same username"}` |
| no username | 400 | `{"errorMessage":"User name is missing"}` |
| `{not json` | 400 | `{"error":"invalid_request","error_description":"Cannot parse the JSON"}` |
| empty, or the literal `null` | **500** | `{"error":"unknown_error","error_description":"For more on this error consult the server log."}` |
| unrecognised field | 400 | `{"error":"Invalid json representation for UserRepresentation. Unrecognized field \"nosuchfield\" at line 1 column 50."}` |

**The 201 sends `content-length: 0`**, where the client create sends no
`Content-Length` header at all. Neither sends a `Content-Type`.

**An empty body is a 500**, where a malformed one is a 400. Same family of
defect as `DELETE .../client-secret/rotated`, and reproduced for the same
reason.

**The unrecognised-field message carries Jackson's line and column**, and the
column points past the *value*, not the field name. Gloak records it and does
not serve it: Go's decoder reports the field name and no position.

### The username is lowercased, and does not change

A create naming `Probe-UPPER` answers 201 and the user reads back as
`probe-upper`.

A `PUT` naming a different, free username answers 204 and **leaves the stored
username alone** - the master realm has username editing switched off. A `PUT`
naming a username somebody else holds still answers 409, so the conflict check
runs before the change is discarded.

`PUT` merges: a request carrying only `firstName` leaves `lastName` and
`email` as they were.

**Attributes sent on create are dropped.** A create carrying
`{"dept":["eng"]}` answers 201 and the user reads back with no `attributes` at
all, because unmanaged attributes are off by default in the declarative user
profile.

### ClientRepresentation carries a description

`description` sits between `name` and `rootUrl`, and none of the six
bootstrapped clients has one - so no golden covered it and Gloak had no such
field at all. `kcadm.sh` found it: `kcadm update clients/{id} -s
description=...` answered 204 and the value vanished on the read back.

That is the first thing the external oracle caught, and the class of gap it
exists for: the conformance suite compares only what a case asks for, and no
case had ever asked for this.

## Credentials

Measured 2026-08-23.

### The credential list carries no secret

`GET /admin/realms/{realm}/users/{user-id}/credentials` answers 200 with an
array, and a user with none gets `[]`. `view-users` is enough, because there
is nothing secret in it:

```json
[{"id":"…","type":"password","userLabel":"office laptop","createdDate":1787481895477,"credentialData":"{\"hashIterations\":5,\"algorithm\":\"argon2\",\"additionalParameters\":{\"hashLength\":[\"32\"],\"memory\":[\"7168\"],\"type\":[\"id\"],\"version\":[\"1.3\"],\"parallelism\":[\"1\"]}}"}]
```

No `value`, no `salt`, no `secretData`. **`credentialData` is a JSON string,
not a nested object**, so the response carries it escaped.

`userLabel` sits between `type` and `createdDate` and is absent when there is
none.

**`additionalParameters` is a Java map inside that string**, in hash order:
`hashLength, memory, type, version, parallelism`. `Case.UnorderedKeys` cannot
reach it - it normalises objects in the JSON document, and this one is inside a
string value - so Gloak writes the five keys out in the measured order rather
than marshalling a Go map. That is the second retreat from letting
`encoding/json` decide key order, after the client `attributes` case, and it
goes the other way: here the order is reproduced rather than given up on.

### reset-password ignores the type it is given

`PUT .../reset-password` answers 204. A body naming `"type":"otp"` answers 204
too, and **replaces the password credential anyway** - same credential id,
refreshed `createdDate`, `userLabel` cleared. The endpoint sets a password
whatever it is told.

A body with no `value` answers 400 `{"error":"No password provided"}` - the
bare-prose shape, which is a third error family on the user endpoints alongside
`errorMessage` and the OAuth one.

`"temporary":true` adds `UPDATE_PASSWORD` to the user's `requiredActions`, and
`false` removes it, so the flag is not write-once. That is the only observable
difference it makes.

### userLabel takes text/plain

`PUT .../credentials/{id}/userLabel` consumes `text/plain`. Sending
`application/json` answers **415**:

```json
{"error":"The content-type header value did not match the value in @Consumes"}
```

which is why its 204 omits `X-Frame-Options` - see the Content-Type rule above.

### Reordering, deleting and disabling

| Request | Status | Body |
|---|---|---|
| `POST .../moveToFirst` | 204 | empty |
| `POST .../moveAfter/{id}` | 204 | empty, **even when the target does not exist** |
| either, unknown credential | 404 | `{"error":"Credential not found"}` |
| `DELETE .../credentials/{id}` | 204 | empty, `Cache-Control: no-cache` |
| `DELETE`, again | 404 | `{"error":"Credential not found"}` |
| `DELETE`, unknown user | 404 | `{"error":"User not found"}` |
| `PUT .../disable-credential-types` | 204 | empty |

`moveAfter` checks only the credential being moved, not the target.

A request naming an unknown user and a real credential answers **"User not
found"**, so the user is resolved first.

**"Credential not found" is a fourth not-found spelling**, after "Could not
find client", "User not found" and "Realm not found." with its full stop.

`disable-credential-types` answers 204 for any list, including `["password"]`,
and nothing observable changes: the credential stays and the user's
`disableableCredentialTypes` stays `[]`. On a bootstrapped master realm no
credential type declares itself disableable, so the endpoint does nothing -
and that is the contract, not a gap.

### Which role each credential operation needs

| Operation | `view-users` | `manage-users` |
|---|---|---|
| `GET .../credentials` | 200 | 200 |
| `PUT .../reset-password` | 403 | 204 |
| `DELETE .../credentials/{id}` | 403 | 204 |
| the reorder and label endpoints | 403 | 204 |

## User logout

Measured 2026-08-23.

`POST /admin/realms/{realm}/users/{user-id}/logout` answers **204** and ends
every session the user holds. It needs `manage-users`; `view-users` gets 403.

It is **idempotent**: a user who is already logged out gets 204 too, so
"nothing to end" is a success rather than a 404. An unknown id still answers
`{"error":"User not found"}`.

The 204 carries no `Cache-Control` and, sent without a `Content-Type`, no
`X-Frame-Options`. The same request with `application/json` carries the header
- an eighth confirmation of the Content-Type rule above and the first on a
`POST`.

### The logout stamps the user's notBefore

Its effect is visible beyond the status code: the user representation's
`notBefore` goes from 0 to the Unix second the logout happened. Nothing else
measured so far writes that field.

### A dead session and a bad token answer differently

A refresh token whose session has been ended answers:

```json
{"error":"invalid_grant","error_description":"Session not active"}
```

where a token that was never valid answers `"Invalid refresh token"`. Same
status, same code, different description. **Both an admin logout and a token
revocation produce the first**, which corrects P1: its revocation test
asserted "Invalid refresh token" from a guess, and that assertion had never
been measured.

Two neighbouring causes are still unmeasured and are left on the
"Invalid refresh token" branch rather than guessed at: a token that has simply
expired, and one minted for a different client.

## Roles

Measured 2026-08-23 while scoping P2's second cut, against a live 26.7.1.

### RoleRepresentation has two serialisations

A **listing** - `GET /roles`, `GET /clients/{uuid}/roles`, every composite
listing and every role-mapping body - carries six keys:

```
id, name, description, composite, clientRole, containerId
```

A **single read** - `GET /roles/{name}`, `GET /roles-by-id/{id}` - carries
seven, the same plus `attributes` last:

```json
{"id":"...","name":"admin","description":"${role_admin}","composite":true,"clientRole":false,"containerId":"<realm uuid>","attributes":{}}
```

That is the same split `briefRepresentation` makes on the listing, and the
listing's default **is** the brief one: `?briefRepresentation=false` adds
`attributes`, `true` and the default omit it. A user listing defaults the other
way round, so the two flags do not mean the same thing in the same place.

`description` is **absent** when the role has none - a role created with only a
name reads back with six keys and no `description`.

`containerId` is the **realm's UUID** for a realm role and the **client's UUID**
for a client role. Not the realm name, and not the clientId.

**Role `attributes` are stored**, unlike a user's, which the declarative user
profile drops. `{"k":["v"]}` round-trips through `PUT` and comes back on the
next read.

### The realm role listing is not sorted

```
offline_access, uma_authorization, create-realm, default-roles-master, admin
```

Neither alphabetical nor the Java map order of the "Java map key order" section
- both were checked. It looks like creation order, but the five names above are
too few to tell creation order from any other unstable one, and the three runs
below show it is not stable at all.

**This describes the unpaginated listing only.** A request that pages - see
"Role listing: first and max" below - is sorted by name instead, and that
sorted order *is* stable. An earlier version of this paragraph ended "and
`first`/`max` page in that same order", which the measurement in that section
contradicts twice over: the paged path sorts, and it is not always reached.

**It does not survive a container restart.** Measured across three
consecutive fresh containers, before P2's roles plan was written:

```
run 1: probe-child, offline_access, uma_authorization, x-manage-realm,
       create-realm, default-roles-master, probe-parent, admin
run 2: create-realm, default-roles-master, offline_access, uma_authorization, admin
run 3: uma_authorization, create-realm, default-roles-master, admin, offline_access
```

Run 1 still carried probe roles from an earlier session, so it has eight names
rather than five; the five bootstrapped names are in a different relative
order in all three runs regardless. It behaves like a Java set, the same as
`scopes_supported`, the token response's `scope` and the JWKS `keys` array,
all of which were found unstable across restarts too.

That is why nothing pins this order. Gloak sorts the listing by name, which is
deterministic, and the conformance case says so with `Case.Unordered` over the
document root - a golden pinning an unstable order fails for no reason. The
comments on `listRealmRoles` in `internal/admin/roles.go` and on the case in
`internal/conformance/catalog_admin.go` refer to this measurement.

### `search` on the role listing is a substring over name *and* description

Three measurements, each ruling something out:

| Query | Matches | Rules out |
|---|---|---|
| `adm` | `admin` | nothing on its own |
| `ealm` | `create-realm` | prefix matching |
| `{role_default-roles}` | `default-roles-master` | name-only matching |

Case-insensitive: `ADM` and `adm` both find `admin`. This is a third filter
family, after the user listing's substring fields and its prefix `search`.

### Role listing: first and max

**The listing pages when `search` is non-empty, or when `first` and `max` are
both present.** Either condition on its own is enough; a request carrying
neither is answered with every role, unpaginated. The paged path is sorted by
name, the unpaginated one is not sorted at all.

An earlier version of this section said pagination takes effect only when
`search` is non-empty. That was wrong, and it was wrong in a specific way
worth recording: it was inferred from three no-`search` probes - `max=2`,
`first=1`, and `first=-1&max=-1` - none of which sends both bounds positive.
The rule's central case had never been issued. It was measured on 2026-08-26
and the answer is below.

alone is `gloak-pg-i` … `gloak-pg-z`, not `gloak-pg-z` … `gloak-pg-i`. The
`(none)`, `max=5` and `first=1` rows come back in the unstable order the
"realm role listing is not sorted" section above records. This also corrects
the older claim, below, that a `search` result comes back in creation order:
it does not, and the `-a`/`-b`/`-c` probe set could not have told the
difference.

**This explains the order difference the older rows recorded and could not
account for.** `first=-1&max=-1` came back sorted while `max=2` and `first=1`
came back unsorted. Under a "search only" rule all three take the identical
path and must be byte-identical, which they were not. Under the measured rule
they do not: `first=-1&max=-1` has both bounds present, so it takes the paged,
name-sorted path, where a negative bound then means "no bound" rather than "do
not page". `max=2` and `first=1` send one bound each and take the unpaginated
path. `first=-1&max=5` and `first=1&max=-1` confirm the sign is irrelevant to
the gate: both page, and both are sorted.

**An empty `search` is not a non-empty one.** `search=&max=2` returns all 23
unsorted, exactly as `max=2` does, while `search=&first=1&max=5` returns the
same five roles as `first=1&max=5`. The empty value neither opens the gate nor
closes it; only the two bounds matter on those rows.

**`max` is a page size, `first` a zero-based offset**, both counted over the
sorted order. `first=0&max=5` takes the first five, `first=5&max=5` takes the
five starting at index 5, `max=0` is an empty array rather than everything, and
a `first` past the end (`first=99` over 23 roles) is `[]`, not an error.

### Writing a role

| Request | Status | Body |
|---|---|---|
| `POST /roles` | 201 | empty, `Location` and `content-length: 0` |
| `POST` a name that exists | 409 | `{"errorMessage":"Role with name probe-role already exists"}` |
| `POST` with no name | 400 | `{"error":"role has no name"}` |
| `GET`/`PUT`/`DELETE` a missing role | 404 | `{"error":"Could not find role"}` |
| `PUT` with no name | 400 | `{"error":"role has no name"}` |
| `PUT` | 204 | empty |
| `DELETE` | 204 | empty, `Cache-Control: no-cache` |

**`Location` names the role by name, not by id**:
`http://host/admin/realms/master/roles/probe-role`. The client and user creates
both put a UUID there.

Three of those bodies are three different error families on one endpoint: the
RFC-ish `{"errorMessage"}` for the conflict, the bare `{"error"}` carrying
lowercase prose for the missing name, and the bare `{"error"}` carrying
sentence case for the missing role.

### `PUT` on a role replaces; `PUT` on a client or a user merges

Measured directly. A role carrying `description` "a probe", updated with
`{"name":"probe-renamed"}` alone, comes back **with no description**. The
client and user updates next door unmarshal the body over the current
representation and keep what the caller omitted.

**A role can be renamed.** `PUT` with a new `name` answers 204, the id survives,
and the old path 404s. A user's username, by contrast, is immutable through its
own `PUT`.

**`composite` in the `PUT` body is ignored, not applied.** A role with no
children, `PUT` with `{"name":"...","composite":true}`, answers 204 and reads
back `composite:false` with no children - the field is server-computed from
the role's own children (see "The parent's own `composite` flag is derived,
not latched" below) and a write cannot set it directly. Gloak already does
this: `applyRoleUpdate` copies `current.Composite` onto the updated role and
never reads `rep.Composite` from the body, so this matches.

### Composites

`POST` and `DELETE` on `.../composites` both take an **array of role
representations** in the body and answer 204. `id` is what they act on.

`GET .../composites` returns realm and client children mixed, in the brief
serialisation. `.../composites/realm` and
`.../composites/clients/{targetClientUuid}` are filters over the same list.
**The brief serialisation holds regardless of `briefRepresentation`** -
`?briefRepresentation=false` on `GET /roles/admin/composites` was checked
directly and still comes back with six keys and no `attributes`, unlike the
plain role listing next door where the same parameter adds it.

**The parent's own `composite` flag is derived, not latched.** It flips to
`true` when the first child is added and back to `false` when the last one is
removed, both unprompted, measured on the same role in the same session:
`probe-parent-realm` read `composite:true` once `probe-child-realm` was added
and `composite:false` again once that same child was removed. The rule is
"has at least one composite child", checked fresh, not a flag that only ever
moves one way. Neither store driver recomputes this on
`AddComposite`/`RemoveComposite`, so the handler does: after every
`POST`/`DELETE .../composites`, it re-lists the role's children and writes
the flag to match whether any remain, rather than setting it unconditionally
on add.

**`POST .../composites` validates the whole batch before applying any of
it.** A body with one valid role id and one that does not exist - tried both
orders, valid-first and invalid-first - answers 404
`{"error":"Could not find composite role"}` and leaves the role with **no**
children at all, not the valid one alone. That is an eighth spelling of
not-found (see the tally below) and it is specific to this endpoint - it is
not `writeRoleNotFound`'s "Could not find role".

`eachComposite` in `internal/admin/roles.go` now matches this: it validates
every id in the batch in a first pass before applying any of them in a
second, so a bad entry anywhere in the body leaves the role's children
untouched and answers `writeCompositeRoleNotFound`'s
`{"error":"Could not find composite role"}`, not `writeRoleNotFound`'s
"Could not find role". `DELETE .../composites` shares the same function and
was kept consistent with `POST` on this, absent a measurement showing the two
differ - removing a child that is not attached is still a no-op 204, since
that id resolves to a real role and only fails the *attached* check inside
`RemoveComposite`, not the existence check above it.

### `/roles/{name}/users` is direct holders only

Not transitive. The administrator holds `admin`, which is composite over
`create-realm`; `GET /roles/admin/users` returns the administrator and
`GET /roles/create-realm/users` returns `[]`.

The user representation there carries **no `access` block** - a fourth
serialisation of a user, matching the service-account one.

`/roles/{name}/groups` answers `[]` on a realm with no groups.

### `roles-by-id` is the same resource by a different key

Same representation, same composite sub-resources. Its 404 is a **different
message**: `{"error":"Could not find role with id"}`.

**Resolving the role happens before the caller is judged, so this 404 always
comes out ahead of any 403** the guard would otherwise answer: a missing role
id is 404 whatever the caller holds, and an existing one the caller may not
see is 403. That lets an unauthorized caller tell "does not exist" apart from
"exists, but I may not touch it" - exactly the ordering an access-control
design would normally avoid. It is Keycloak's own measured order, not a
defensive choice. An earlier version of this project's own plan reasoned it
the other way round, as if enforcing 404-first were what *avoided* the leak;
it is what causes it.

That makes eight spellings of not-found measured so far: `Could not find
client`, `User not found`, `Realm not found.` with its full stop, `Credential
not found`, `Could not find role`, `Role not found`, `Could not find role with
id`, `Could not find composite role`. A ninth arrived with the client
role-mapping reads: `Client not found`, which is the *mapping* routes' answer
for an unknown client UUID where the client and role endpoints send `Could not
find client` for the very same UUID. See "A client UUID that resolves to nothing
has its own not-found spelling" below.

### Which role each role operation needs

Measured by giving a user exactly one `master-realm` role and trying each
operation, the same method the client and user tables used, then re-measured
for Task 9 against the paired manage role too, because the first pass only
tried the view role of each pair and looked like a lone requirement.

| Operations | Read | Write |
|---|---|---|
| `/roles`, `/roles/{name}`, their composites and `.../groups` | `view-realm` **or** `manage-realm` | `manage-realm` of the role's own family - a composite write with a cross-family child needs more, see below |
| `/clients/{uuid}/roles/...` and its composites and `.../groups` | `view-clients` **or** `manage-clients` | `manage-clients`, same caveat |
| `/roles-by-id/{id}/...` | follows the resolved role's container: the same either/or pair, picked by the role's own family rather than by the route | the manage role of the role's own family, same caveat |
| `.../roles/{name}/users` (both forms) | **a conjunction, not an either/or**: one role from the row above, **and** one of `view-users`/`manage-users`/`query-users`, held together - neither family alone opens it, and two roles from the same family do not either | n/a, no write |

**"Read" means either role of the pair, not the view role alone**, checked
directly on the plain reads, the composite listings and `.../groups`, on both
realm roles and client roles - the tables further down carry the raw
pairwise results. The plan behind this cut assumed a single required role
four separate times, and the paired manage role opened the operation every
time it was actually tried.

**The write column above is the same-family case.** A composite write
(`POST`/`DELETE .../composites`) whose body carries a child from the *other*
family needs the child's own manage role too, and only on `POST` - `DELETE`
does not enforce it, in either direction; see the cross-family table below.
`POST .../composites` also validates every id in the batch before applying
any of them, and a batch mixing a bad id with a forbidden cross-family child
is decided by **array order**: whichever bad entry comes first is the error
returned. The `composite` flag itself is not part of either column - it is
derived from whether the role currently has children, recomputed after every
add and remove rather than stored.

`roles-by-id` is the interesting one: the guard is decided by the data, not by
the route. A client role reached by id needs `view-clients` or
`manage-clients`; a realm role reached by the same path needs `view-realm` or
`manage-realm` - the same view/manage pair the by-name reads take, just picked
by the resolved role's container instead of by the route. `view-users`,
`manage-users`, `query-clients` and `query-users` are refused everywhere in
this table - **except `.../users` below, where the first two of those are half
of what it takes.**

**Re-measured for Task 9, because the first pass only tried `view-realm` and
`view-clients`.** That looked like a lone required role each and was recorded
that way once already; trying `manage-realm` and `manage-clients` too, on both
a realm role id and a client role id, shows they open the read side exactly

**The write side is narrower, and single for `PUT`, `DELETE`, and for

measurement session fetched all seven role representations sequentially
before minting the probe user's token, on tokens that last 60 seconds.
Re-measured with role representations cached up front and a token minted
immediately before each call, exactly as prescribed for the token-expiry
problem: `200 | 200`, consistent with every pairwise result already in this
section. The table cell above now reads the corrected value; the old one -
`200 | 403` - is spelled out here rather than left to a diff, because a
reader who previously saw `403` needs to know it was wrong and why, not just
that the number changed.

Gloak's `guardAny(realmRolesReadRoles, ...)` / `guardAny(clientRolesReadRoles,
...)` from the plain reads cannot express a two-family conjunction, so
`.../users` is registered with a new combinator, `guardAnyAndAny`, built from
`guardAnyRejecting` rather than duplicated - see `internal/admin/router.go`.
The corrected measurement does not change this: `guardAnyAndAny` already
grants 200 to a caller holding all seven roles on both routes, since holding
all seven means both `hasAny` checks pass regardless of side.

**`POST /clients/{master-realm uuid}/roles` is 403 for a full administrator.**
The realm's own client will not take new roles from anybody, which is the same
rule as "the realm's own client is never configurable" in the client section.

**The same refusal extends to writing composites on a role the realm's own
client already has, not just to creating a new one.** Measured against a live
26.7.1 with the full administrator token, on **both** composite verbs,
re-measured 2026-08-25:

```
POST /admin/realms/master/clients/{master-realm uuid}/roles/query-groups/composites
Authorization: Bearer <full administrator token>
Body: [{"id":"...","name":"probe-child"}]

HTTP/1.1 403 Forbidden
{"error":"HTTP 403 Forbidden"}
```
```
DELETE /admin/realms/master/clients/{master-realm uuid}/roles/query-groups/composites
Authorization: Bearer <full administrator token>
Body: [{"id":"...","name":"probe-child"}]

HTTP/1.1 403 Forbidden
{"error":"HTTP 403 Forbidden"}
```
```
GET /admin/realms/master/clients/{master-realm uuid}/roles/query-groups/composites

HTTP/1.1 200 OK

```

Even the bootstrapped administrator, which passes every guard in this
document, is refused on the two writes - the same "realm's own client is never
configurable" rule, applied to an existing role's composites rather than to
creating one. The read is not refused, so the rule is on the writes alone.
The `DELETE` and the `GET` are new with this re-measurement; only the `POST`
had been recorded before, and the `DELETE` was not assumed from it - this
document already has one case (the cross-family child rule) where `POST` and
`DELETE` were measured and turned out to differ.

**Gloak matched this from 2026-08-25.** It had answered 204 to the identical
request, which is worse than a cosmetic divergence: a caller holding only
`manage-clients` could `POST` a composite onto `master-realm`'s own
`manage-clients` role naming **`manage-realm`** as the child, and every check
passed - the route guard wants `manage-clients`, and the per-child
`requiresChildManageRole` wants `manage-clients` too, because `manage-realm`
is itself a client role on that same client. `roles.Effective` then returned
`manage-realm` on the next request. Nothing outside could mint a narrow-role
admin at the time, so it was not reachable, but role assignment is the next
cut.

**The check is in `eachComposite`, not in `clientRoleContainer`.** An earlier
revision of this passage said the fix belonged in `clientRoleContainer`,
which `roles-by-id` "already shares" through `clientRoleLocator`. That was
wrong, and a follow-up obeying it would have shipped half a fix: the
`roles-by-id` routes do not go through `clientRoleContainer` at all.
`guardByRoleContainer` in `internal/admin/router.go` resolves the role with
`Roles().ByID` and hands it to `byIDLocator`, so `POST
/roles-by-id/{master-realm client role id}/composites` would have stayed
open. `eachComposite` is the one place the by-name and by-id families meet,
and both are covered by
`TestTheRealmsOwnClientRefusesCompositeWrites`.

The refusal is scoped to the two composite writes, because that is what was
measured. `PUT` and `DELETE` of the realm's own client's roles are **not**
refused by Gloak and Keycloak's behaviour there is unmeasured - see F26 in
`2026-08-18-gloak-followups.md`.

### Adding an admin role as a composite is judged against the *caller*, not the role

Measured 2026-08-25 against a plain `docker run` of 26.7.1, chasing whether
the realm side has the same escalation the `master-realm` client side had. It
does not, and the reason is a rule this document had not recorded at all.

The suspected path was: a caller holding only `manage-realm` does `POST
/admin/realms/master/roles/default-roles-master/composites` naming the
`admin` role's id. Realm parent, realm child, so the route guard and the
per-child `requiresChildManageRole` check both pass, and `admin` lands on the
role every user in the realm holds. **Keycloak refuses it**, but not because
of anything about `default-roles-master`:

| Caller | Parent | Child | Status |
|---|---|---|---|
| full administrator | `default-roles-master` | `admin` | 204 |
| full administrator | `default-roles-master` | `probe-child` (ordinary) | 204 |
| full administrator | `probe-parent` (ordinary) | `admin` | 204 |
| only `manage-realm` | `default-roles-master` | `admin` | **403** |
| only `manage-realm` | `default-roles-master` | `probe-child` (ordinary) | 204 |

So the parent does not matter and the child alone does not matter: **the same
request is 204 for one caller and 403 for another.** The full administrator,
which holds `admin`, may do it; a `manage-realm` holder may not.

Swept over every child a caller holding `manage-realm` **and**
`manage-clients` could name - both roles held so that the cross-family
per-child rule above is not what is being measured - against an ordinary realm
role as the parent, with the full administrator run beside it as a control:

| Child (master-realm client roles) | `manage-realm`+`manage-clients` | full admin |
|---|---|---|
| `create-client` | 204 | 204 |
| `impersonation` | **403** | 204 |
| `manage-authorization` | 204 | 204 |
| `manage-clients` | 204 | 204 |
| `manage-events` | **403** | 204 |
| `manage-identity-providers` | **403** | 204 |
| `manage-organizations` | 204 | 204 |
| `manage-realm` | 204 | 204 |
| `manage-users` | **403** | 204 |
| `query-clients` | 204 | 204 |
| `query-groups` | 204 | 204 |
| `query-organizations` | 204 | 204 |
| `query-realms` | 204 | 204 |
| `query-users` | 204 | 204 |
| `view-authorization` | 204 | 204 |
| `view-clients` | 204 | 204 |
| `view-events` | **403** | 204 |
| `view-identity-providers` | **403** | 204 |
| `view-organizations` | 204 | 204 |
| `view-realm` | 204 | 204 |
| `view-users` | **403** | 204 |

| Child (realm roles) | `manage-realm`+`manage-clients` | full admin |
|---|---|---|
| `admin` | **403** | 204 |
| `create-realm` | **403** | 204 |
| `default-roles-master` | 204 | 204 |
| `offline_access` | 204 | 204 |
| `probe-child` | 204 | 204 |

Two things this rules out. It is **not** "the caller must hold the child":
the caller held neither `view-realm` nor `probe-child` and got 204 for both.
It is **not** a fixed list of forbidden children either: the full
administrator's column is 204 throughout, and the refused set moves when the
caller changes. Granting the same caller `manage-users` and re-running the
refused set:

| Child | before | after granting `manage-users` |
|---|---|---|
| `view-users` | 403 | **204** |
| `manage-users` | 403 | **204** |
| `query-users` | 204 | 204 |
| `impersonation` | 403 | 403 |
| `view-events` | 403 | 403 |
| `manage-events` | 403 | 403 |
| `view-identity-providers` | 403 | 403 |
| `manage-identity-providers` | 403 | 403 |

The rule is therefore: **a caller may attach an admin role as a composite only
if it already has the administrative power that role confers.** `manage-realm`
carries `view-realm` and the realm-shaped roles with it, `manage-clients`
carries `view-clients`/`create-client`/the authorization pair, `manage-users`
carries `view-users`, every `query-*` role is open to any of these, and
`impersonation`, the events pair, the identity-provider pair, `admin` and
`create-realm` each need themselves. Ordinary, non-admin roles are never
checked this way.

**Gloak does not implement this and answers 204 throughout.** It is a live
privilege-escalation path the moment a narrow-role admin can be minted, and it
is not implemented here on purpose: the naive version - refuse when the caller
does not hold the child - is falsified by fourteen 204s in the table above,
so a partial implementation would diverge in the *too restrictive* direction,
which this branch has already been burned by once on the `DELETE .../composites`
cross-family rule. The same check governs role assignment to a user, which is
a later cut, so it wants one deliberate task covering both. Tracked as F28 in
`2026-08-18-gloak-followups.md`.

#### `clientMappings` is a Java HashMap, and Gloak must not sort it

The keys come back in **HashMap bucket order**, the same thing
`resource_access` does in the token package. This was measured rather than
carried over from the token half, because nothing says two different Keycloak
resources build their maps the same way.

A two-client subject is enough to rule out sorting. `probe-two` holds `zrole`
on `zeta-client` and `arole` on `alpha-client`, assigned in that order:

```
$ curl -s -H "Authorization: Bearer $T" "$KC/admin/realms/master/users/$PU/role-mappings"
{"realmMappings":[{"id":"16c28093-1f02-4e25-aee4-01b69c585e13","name":"default-roles-master","description":"${role_default-roles}","composite":true,"clientRole":false,"containerId":"67280e0f-c53f-413d-9a7c-2e3b245a7b92"}],"clientMappings":{"zeta-client":{"id":"b6155b94-b5c6-45ea-ae56-67d2fde4965f","client":"zeta-client","mappings":[{"id":"53074858-ff57-451f-9269-ba02e396a4af","name":"zrole","composite":false,"clientRole":true,"containerId":"b6155b94-b5c6-45ea-ae56-67d2fde4965f"}]},"alpha-client":{"id":"ec13c347-8931-4f1f-a82a-e4bb19939695","client":"alpha-client","mappings":[{"id":"01677a98-89c5-4b5d-b543-b565180d530f","name":"arole","composite":false,"clientRole":true,"containerId":"ec13c347-8931-4f1f-a82a-e4bb19939695"}]}}}
```

`zeta-client` before `alpha-client`, so a Go map would get it backwards. But
that pair alone does not separate bucket order from *insertion* order, since
`zeta-client` was assigned first. A six-client subject does. `probe-six` holds
one role on each of `cx1`..`cx6`, with the clients created, the roles created
and the assignments made in that order:

```
$ curl -s -H "Authorization: Bearer $T" "$KC/admin/realms/master/users/$PS/role-mappings" | python3 -c 'import sys,json,collections;d=json.load(sys.stdin,object_pairs_hook=collections.OrderedDict);print(list(d["clientMappings"].keys()))'
['cx6', 'cx5', 'cx2', 'cx1', 'cx4', 'cx3']
```

Sorted would be `cx1..cx6`; insertion would be `cx1..cx6`; the answer is
neither. It is exactly what `javamap.KeyOrder` predicts, because the six land
in six distinct buckets at capacity 16:

```
  cx1            bucket 13
  cx2            bucket 12
  cx3            bucket 15
  cx4            bucket 14
  cx5            bucket  1
  cx6            bucket  0
```

so bucket order is `cx6(0), cx5(1), cx2(12), cx1(13), cx4(14), cx3(15)`. The
`zeta-client`/`alpha-client` pair is buckets 6 and 13, which is why that one
also comes out reversed.

**So this endpoint gets `internal/javamap`, not a second `Case.UnorderedKeys`
retreat.** The one documented retreat stays the only one.

#### Where javamap still cannot follow, and why that changes nothing here

A third vector was taken and `javamap` got it **wrong**, which is worth writing
down rather than hiding. `probe-five` holds one role on each of `one`, `two`,
`three`, `four`, `five`, assigned in that order:

```
$ curl -s -H "Authorization: Bearer $T" "$KC/admin/realms/master/users/$PF/role-mappings" | python3 -c 'import sys,json,collections;d=json.load(sys.stdin,object_pairs_hook=collections.OrderedDict);print(list(d["clientMappings"].keys()))'
['four', 'one', 'two', 'five', 'three']
```

`javamap.KeyOrder` predicts `[four one five three two]`. The buckets say why:

```
  one            bucket  7
  two            bucket 13
  three          bucket 13
  four           bucket  6
  five           bucket 13
```

`two`, `three` and `five` collide three ways in bucket 13, and colliding keys
chain in **insertion** order, which nothing observable reports - `javamap`
breaks such ties alphabetically and got `five, three, two` where Keycloak says
`two, five, three`. That is the limitation `internal/javamap`'s own doc comment
already names, measured a second time here rather than newly discovered. The
prefix `four, one` - the two keys with buckets to themselves - is right.

This does not weaken the decision above. `javamap` is exact whenever the client
ids in play do not collide, and it is the only thing that gets the non-colliding
case right at all; sorting is wrong even there. A conformance case whose
fixture happens to collide has to say so with `Case.UnorderedKeys`, exactly as
`internal/javamap` already instructs.

### Which role a role mapping needs

| Operations | Read | Write |
|---|---|---|
| `/users/{id}/role-mappings` | `view-users` **or** `manage-users` | - |
| `/users/{id}/role-mappings/realm[/available\|/composite]` | `view-users` **or** `manage-users` | `manage-users` |
| `/users/{id}/role-mappings/clients/{uuid}[/available\|/composite]` | `view-users` **or** `manage-users` | `manage-users` |

**The guard follows the subject, not the role.** Assigning a `master-realm`
client role to a user needs `manage-users` and not `manage-clients`; a caller
holding `manage-realm` and nothing else is refused on all of them. That is the
opposite of `roles-by-id`, where the guard follows the role's container.

This table said "every `/users/{id}/role-mappings/...`" until 2026-08-26. That
phrasing covered more than the sweeps behind it: they were the three realm reads
and the two realm writes, and nothing on the `clients/{uuid}` locator. Both
halves have since been swept there too - "The full single-role sweep of the
three client reads" and "...of the two client writes" below - and each agrees
with its realm mirror, so all four cells are now measured on the routes they
name. The row stays split because the sweeps were four, not two.

The combined view got the row of its own added 2026-08-26, on its own sweep of
the same seven callers - "The full single-role sweep of the combined view"

So the client triple is the realm triple exactly: `.../clients/{uuid}` and
`.../clients/{uuid}/available` **ignore the parameter entirely**,
`.../clients/{uuid}/composite` honours it, defaults to brief, and sends the
role's real attributes when it is `false`. `briefRepresentation=true` is
indistinguishable from omitting it on all three.

### `available` is filtered by what the caller may grant

The list is **not** simply "every realm role not assigned directly". Keycloak
also drops the roles the *caller* is not entitled to hand out. Measured on one
subject, `probe-subject`, which holds `probe-attr` and `default-roles-master`
directly, with three different callers:

```
--- caller probe-view-users ---
    []
--- caller probe-manage-users ---
    ['offline_access', 'uma_authorization']
--- caller admin ---
    ['create-realm', 'offline_access', 'uma_authorization', 'admin']
```

All three are 200. The full administrator's answer is exactly the complement of
the direct assignments; `manage-users` loses `admin` and `create-realm`, which
it may not grant; and `view-users` loses everything, because it may not grant
any role at all - it can read the list and assign nothing.

This is the same caller-relative predicate recorded under "Adding an admin role
as a composite is judged against the *caller*, not the role", applied to a read
rather than a write. Its rule is derived in the F28 task; until then Gloak
answers the administrator's list to every caller its guard admits.

## A wrong method is not always 404

Measured 2026-08-26 while establishing that `POST /users/{id}/role-mappings` is
not an operation. It is not, but the shape of its refusal is not the one
`AGENTS.md` describes for a wrong method on a known path.

`POST` and `DELETE` answer the wrong-method 404:

```
$ curl -s -o /dev/stdout -w '\nHTTP %{http_code}\n' -X POST -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '[]' "$KC/admin/realms/master/users/$PU/role-mappings"
{"error":"HTTP 404 Not Found"}
HTTP 404
$ curl -s -o /dev/stdout -w '\nHTTP %{http_code}\n' -X DELETE -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '[]' "$KC/admin/realms/master/users/$PU/role-mappings"
{"error":"HTTP 404 Not Found"}
HTTP 404
```
